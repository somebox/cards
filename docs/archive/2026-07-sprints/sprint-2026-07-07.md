## Theme

The last sprint made the machine contract whole; this one gives the human
view hands. Today the board can *show* almost everything and *change* almost
nothing: comments, repeating entries, card creation, and board creation all
require the CLI. Each phase turns one read-only surface into a complete,
demoable editing capability — as a **thin client of existing `/v1` endpoints**
(the standing constraint: the UI is one view over the same API; nothing in
this sprint may add core surface except Phase 4's roadmap-sanctioned reload
endpoint). Phase 3 pays the theme debt down while it's fresh: three themes
now live as intertwined CSS + template branches; themes.md's "themes are
data" extraction makes the next theme a file, not a fork.

## Test infrastructure (cross-cutting, applies to every phase)

Same conventions as last sprint, plus one addition. Every new test is
self-contained and repeatable: in-memory/`t.TempDir()` stores via the
existing harnesses, fixtures through shared helpers (`coretest`), teardown
via `t.Cleanup`, `go test ./...` the one command. UI behavior is pinned at
the httpapi layer (render + endpoint round-trips), not with a browser
driver. **New:** a `docaudit`-pattern CSS sanity test — brace balance and
per-theme selector-prefix discipline for `style.css` — because a single
dropped `}` silently swallowed the entire labels theme this week and nothing
caught it.

### Phase 1 — The modal becomes a work surface: comments + repeating entries (`a09f0455`, `b9e17b9e`)

Add and edit comments, and append/update/remove repeating entries, from the
card modal — plus the entries layout pass, since editing and displaying the
same rows is one design problem. All mutations are thin calls to existing
endpoints (`POST/PATCH .../comments`, `.../entries` append/patch/remove) with
the card's version, reusing the `reloadModal` helper (P4 of last sprint)
after each success and its "card changed — reload" 409 affordance.

- Comment composer at the bottom of the modal (textarea + submit; Escape
  reverts, error in the modal `.alert`); existing comments get an edit
  affordance (author-or-anyone is fine — no auth by design).
  **Outcome:** add + edit comments without leaving the board.
  Files: `card_modal.html`, `layout.html` (JS), `ui.go`
- Repeating-entry editor: "add entry" renders the `item_fields` sub-form from
  the schema (the same definition that drives the API — no hand-built form);
  per-entry edit/remove with confirm on remove.
  **Outcome:** `work_log`/`change_log`-style feeds are writable from the UI;
  agents and humans append to the same evidence stream.
  Files: `card_modal.html`, `layout.html`, `render.go` (entry field views)
- Entries layout (`b9e17b9e`): feed display gets aligned field labels,
  timestamp right-aligned, author chip — one design across default/journal/
  labels themes via role tokens, not per-theme markup.
  **Outcome:** a 10-entry work_log is scannable, not a wall.
  Files: `card_modal.html`, `style.css`
- Tests: httpapi round-trips for comment add/edit and entry append/update/
  remove through the UI save paths; a stale-version entry mutation renders
  the 409 reload affordance; template render test pins the schema-driven
  sub-form for a repeating field with required item_fields.

**Demo:** open a card, add a comment, append a `work_log` entry via the
schema-generated form, edit both, remove the entry — board reflects
everything live; a second tab's stale write gets "card changed — reload".

**Exit criteria:** every comment/entry verb reachable from the modal is a
thin client of an existing endpoint (grep: no new `/v1` routes); reloadModal
reused (no second refresh path); keyboard path works (tab to composer,
submit, revert); suite green.

### Phase 2 — New-card creation via the modal (`adb1ebcf`)

Replace the separate `/ui/cards/new` page flow with in-board creation: the
"+ New Card" affordance (nav + per-lane) opens the modal in create mode —
placeholder title, click-to-edit fields generated from the chosen type's
schema, `POST /v1/cards` on save.

- Type picker first (the workspace's card types with their icons/accents —
  the granular types shipped yesterday make this picker meaningful), then
  the schema-driven field form; required fields marked, enum defaults
  pre-selected, validation errors render per-field from the structured
  `core.Error` (field + message — already on the wire).
  **Outcome:** creating an `api-task` prompts for endpoint/api_change;
  creating a `frontend-task` prompts for surface — the schema drives the
  form, per the philosophy.
  Files: `card_modal.html` (create mode), `layout.html`, `ui.go`, `render.go`
- Lane-aware creation: "+ " in a column pre-sets status to that column
  (validated against the type's `allowed_columns`; disallowed columns are
  disabled in the picker with a title explaining why).
  **Outcome:** cards land where you created them.
- Tests: httpapi create-via-UI round-trip per field type (enum default,
  required-missing → per-field error rendering, allowed_columns
  enforcement); idempotency (double-submit guarded by Idempotency-Key, the
  header the API already honors).

**Demo:** from the board, create a `data-task` in the todo lane: pick the
type (flask icon), fill migration/safety, save — the card appears in todo
with its type spine; submit once with a missing required field and see the
inline error on that field.

**Exit criteria:** `/ui/cards/new` page redirects to (or is replaced by) the
modal flow; no hand-written per-type form markup (one schema-driven
renderer); double-submit creates one card; suite green.

### Phase 3 — Themes as data (`e71a64fa`, `57db13a6`, `72ebfbee`)

Execute themes.md's extraction: themes become pure CSS (+ tokens), with zero
template branches — then finish the labels theme and the modal spacing pass
on the clean substrate.

- Remove the theme conditionals from templates (`{{if eq .Theme "labels"}}`
  font links etc. in layout.html) per themes.md: a theme contributes a CSS
  file/block + optional font preloads declared as data (theme manifest), not
  markup branches. Role tokens (the labels commit started this) become the
  documented contract a theme implements.
  **Outcome:** adding a theme = adding CSS; templates are theme-blind.
  Files: `layout.html`, `style.css` (or split per themes.md), `render.go`
  (theme manifest), `docs/architecture/design-system.md`
- Labels completion (`57db13a6`): comment/link counts + blocked badge return
  inside the compact two-row card (right-aligned in the secondary row);
  blocked stays text, not color-only (a11y).
  **Outcome:** no information lost relative to the default theme.
- Modal spacing/rhythm pass (`72ebfbee`, the modal half — the card half
  shipped with the labels density pass): consistent field grid, section
  rhythm, footer alignment across all three themes via tokens.
- Tests: the new CSS sanity test (brace balance + theme-prefix discipline);
  template render test asserting no `data-theme` conditionals remain in
  template output paths; visual check in all three themes before merge.

**Demo:** switch default → journal → labels on the same board with themes
that are pure CSS; labels cards show counts/blocked; the modal reads
consistently in all three.

**Exit criteria:** `grep -c 'eq .Theme' templates/` returns 0; the CSS
sanity test fails on an unbalanced brace (proven by mutation); labels shows
counts/blocked/badges; design-system.md documents the theme contract; suite green.

### Phase 4 — Create a board from the UI (`f6d2f5ea`; enabler: workspace reload `4b507da7`)

The gated stretch phase — it needs one piece of sanctioned core surface
first: `POST /v1/workspace/reload` (+ `definition_reloaded`, whose event
type already exists), ROADMAP §7's proposed card. Boards are definition
*files* (files where humans review); the UI therefore **writes the file and
asks for a reload** — it does not grow a parallel board store.

- Enabler: `POST /v1/workspace/reload` re-runs the config loader against
  `definitions/`, swaps the workspace atomically on success, emits
  `definition_reloaded`; a load error returns the structured validation
  error and keeps serving the old definitions (never a half-loaded state).
  **Outcome:** definition edits (by hand or by UI) apply without restart —
  valuable on its own even if the rest of the phase slips.
  Files: `internal/config`, `internal/httpapi/api.go`, `internal/core`
  (swap seam), CLI `cards reload`
- Create-board form (modal): name, columns (from workspace columns), card
  types (checkboxes of existing types), optional WIP limit — writes
  `definitions/boards/<id>.json` via a new thin endpoint that validates
  through the same loader before persisting, then reloads.
  **Outcome:** a new board exists as a reviewable JSON file in git, exactly
  as if hand-written.
- Tests: reload round-trip (edit definition on disk → reload → new state
  served; invalid definition → 422 + old state intact); create-board
  end-to-end (file written, matches loader schema, board appears in nav).

**Demo:** create a "design" board from the UI picking two card types; the
file appears in `definitions/boards/`, the nav updates without a restart;
break the file by hand, hit reload, get the validation error while the old
board keeps serving.

**Exit criteria:** reload never leaves a half-loaded workspace (error path
pinned); the written file round-trips the loader; board-settings *editing*
explicitly deferred (`0707a008`); suite green.

## Risks

- Phase 1's entry sub-forms are the sprint's design-heavy center: repeating
  `item_fields` include user/date/enum types — reuse the existing field-edit
  controls or the form forks the schema contract. If it balloons, ship
  comments alone (still demoable) and let entries slip to the next sprint —
  not the reverse.
- Phase 3 before or after Phases 1–2? Template surgery (theme extraction)
  touches the same files as the modal work. Order chosen: P1/P2 first (user
  value), P3 lands on their final markup — reversing would rebase the
  extraction twice.
- Phase 4's reload endpoint is core surface: keep it exactly
  reload-definitions (no hot per-board PATCH API) or it becomes the
  board-settings editor by accident.
- The workflow's dissent (read pool > UI) is a real signal about *load*,
  not *value*: if dogfooding this sprint hits visible board latency from
  serve-side contention, pull `fec18019` forward rather than tuning around
  it.
- Uniform-schema temptation: Phase 2's form generator must consume
  introspection (`GET /v1/workspace`), not duplicate field knowledge in JS.

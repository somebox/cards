## Appendix A — cross-cutting analysis (Fable, the hardest step)

**Foundations to tackle first**
- Event-log integrity before any durable-delivery work: the ClaimAtomic cluster (DEBT-01/02/30/17 in internal/sqlite/sqlite.go:445-456) silently drops event-insert/FTS errors and emits hand-rolled Version:0 events. The outbox tailer, webhooks, and SSE replay all read this log as ground truth; a webhook that never fires because an insert was swallowed is undebuggable. Small, well-scoped, already sequenced as fix #1 in the ledger's own plan — do it first. *(v2 note: review verified this is already fixed at HEAD — reduced to a pin test.)*
- A single Subscriber/Consumer abstraction designed once (short RFC), not three times: the outbox card needs per-consumer durable cursors, the webhook card needs subscriptions (id, URL, filter, HMAC secret, cursor, dead-letter state), and MonitorScheduler's HasSubscriberFor liveness check needs to understand 'disconnected but not caught up'. These are the same concept. Designing it before either build prevents two divergent liveness/interest mechanisms (bus.go SetOnSubscriptionChange vs. tailer cursors) and answers the hooks-Supervisor migration question deliberately.
- Goroutine lifecycle convention (DEBT-29): the hook supervisor already outlives ListenAndServe failure because it isn't tied to server shutdown. The outbox tailer and webhook delivery worker are two more long-lived goroutines about to be added. Establish one pattern (shared context.Context / RegisterOnShutdown) now so all three background workers share it instead of each reinventing shutdown.
- Shared workspace-resource construction helper: attachments need artifacts.Manager constructed from the resolved workspace dir at three call sites (cmd/cards/serve.go for HTTP+MCP, cmd/cards/directcli.go). One helper owning 'workspace dir -> on-disk resource roots' avoids silent divergence between CLI-direct and served-HTTP, and sets the precedent index.md:328's planned release-artifacts will follow.
- Dogfood-with-enforcement as a process foundation: commit the JSONL export as canonical (SQLite demoted to derived artifact) AND add the CI/pre-commit check that doc-cited card short-ids resolve against the committed export. Without the check, the step just reproduces the 21/23-dangling-refs rot one level up. Cheapest candidate (S), and its real usage data is the input for deciding whether the XL outbox is needed at all.
- OpenAPI path-table decision: internal/openapi/openapi.go's hand-authored paths() is already missing links/comments; artifacts and /v1/subscribers each add another manual line. Decide once — generate from the chi router, or add a CI drift check — before two more surfaces widen the gap.
- Cross-surface byte-transport design note: MCP (JSON-RPC/stdio) can only carry base64 while HTTP gets multipart/raw bodies. Settle the encoding, size limits, and 'this asymmetry is intentional' documentation once for attachments, because it will recur for any future binary surface (export downloads, release artifacts).

**Tech debt to clear**
- DEBT-01 + DEBT-02 + DEBT-30 + DEBT-17 (ClaimAtomic hardening, one file/one pass per the ledger's own fix plan) — direct prerequisite for outbox/webhooks and for trusting artifact_added in the log. *(v2 note: verified already fixed at HEAD.)*
- DEBT-29 (supervisor lifecycle not tied to shutdown) — becomes the template bug for the outbox tailer and webhook worker if not fixed before they're written.
- DEBT-57 correction: the ledger still describes artifacts.Manager as 'an empty struct' with nothing implemented; the actual file has full content-addressing, MIME sniffing, and symlink confinement. This stale entry (plus inventory.md's matching description) actively misleads anyone scoping the attachments card — correct it as the first act of that work.
- DEBT-42/43/44 (stale event-catalog counts and 'events_test.go does not exist' claims) — one editing pass; matters because the attachments card adds artifact_added emission and the counts must not drift further.
- DEBT-45/46 (hook payload doc drift: board_ids field that doesn't exist; service-kind autostart contradiction) — needs the product call before webhook becomes a third Extension.Kind reusing the same filter model; resolving the hook contract precisely is a prerequisite for specifying the webhook one.
- Repo hygiene: archive debt-ledger.md / action-plan.md / reorg-plan.md to docs/archive alongside the already-moved review files; commit or restore the pending deletion of docs/plans/sprint-2026-07-05.md so the newest plan's status is unambiguous.
- DEBT-06 (SSE replay error swallowed) rises in priority the moment durable-cursor consumers exist — fix as part of, not after, the outbox work.

**Domain-model evolution to consider**
- Subscriber as a first-class durable entity (id, filter, cursor, delivery state, dead-letter record) — the one genuinely new domain concept underlying outbox, webhooks, hooks-with-replay, and monitor interest. Currently punted three separate times; should be designed once as the unifying model, with SSE Last-Event-ID reframed as a client-held cursor of the same species.
- Static vs. runtime-mutable extensions: /v1/subscribers would be the first API-created extension-like entity in a system whose extension model is entirely file-declared (definitions/extensions.json). Breaking that invariant is a deliberate architectural fork — and because an unauthenticated endpoint registering outbound URLs is an SSRF surface, it drags the ROADMAP §1 auth non-goal forward. Decide the fork (and write the auth design note) before building the surface.
- Explicit delivery-semantics taxonomy per surface (index.md §9): at-most-once shell hooks, pull-based idempotent SSE/feed, at-least-once push webhooks — plus how escalated-condition restart duplication (§8 point 6) compounds with webhook retries. Make the contract table complete before a fourth surface ships.
- Artifact mutation as a first-class service operation: a dedicated Service.AddArtifact method with write-time ArtifactPolicy validation and a proper EventArtifactAdded constructor (payload shape: field id, Meta, overwrite semantics) — completing the existing AddLink/AddComment pattern instead of the current 'stored as-is' generic field patch. This closes, rather than expands, the deliberately-small field-type set.
- Committed JSONL export as the canonical workspace representation, with SQLite as a derived/rebuildable artifact — a source-of-truth inversion, not a schema change. It creates a two-writer problem (live DB vs. git snapshot) whose honest resolution is the deferred D13 git-backed mirror / version-gated PATCH-import; dogfooding should be scoped one-way and treated as the evidence-gathering phase for D13.
- Commit-vs-dispatch decoupling as an explicit contract: once a tailer exists, 'crash after commit, before dispatch' flips from documented tradeoff (index.md §8.5) to regression class. That guarantee change should be written into index.md as a versioned contract, not implied by implementation.

**Sequencing:** Phase 0 (days): clear the cheap load-bearing debt — ClaimAtomic cluster (DEBT-01/02/30/17), DEBT-29 lifecycle pattern, ledger/doc refresh (DEBT-42-46, DEBT-57 correction), repo hygiene (archive root artifacts, resolve sprint-plan deletion). This unblocks everything and nothing depends on anything else. Phase 1 (parallel, independent tracks): (a) dogfood-own-backlog (S) with the doc-id CI check — it generates the real usage signal that determines whether the XL outbox is justified, and gives every later feature a live test bed; (b) wire-attachments (M) — it touches core/httpapi/mcp/cli but not the events-delivery path, so it can proceed independently once the shared Manager-construction helper and the byte-transport design note exist; route-level adversarial path-traversal tests are its gate. Phase 2 (gated on design): write the Subscriber RFC (unified cursor/liveness/dead-letter model, hooks-migration decision, static-vs-runtime extension fork, auth/SSRF note for /v1/subscribers). Do not start the outbox before this RFC — its two biggest risks (duplicate liveness models, hooks-migration ambiguity) are design failures, not coding failures. Phase 3: build outbox + webhooks as one sequenced effort with webhooks as the outbox's first real consumer — the webhook card is what makes Step 4 necessary rather than speculative infrastructure, and building the outbox alone would repeat the over-investment pattern its own risk list warns about. Net: dogfooding unblocks the outbox go/no-go decision; the ClaimAtomic fix unblocks all durable delivery; the Subscriber RFC unblocks both Phase-3 builds; attachments is unblocked immediately and blocks nothing.

## Appendix B — candidates considered
- **Wire attachments end-to-end (upload + serve + CLI verb + MCP tool + emit artifact_added)** — This is the highest-leverage, lowest-risk net-new capability within reach because the hard, dangerous part is already built and tested: the content-addressed store (internal/artifacts) has SHA-256 addressing, MIME sniffing, and path-confinement (DEBT-57) done. What remains is thin, well-understood surface plumbing — an upload endpoint, a serve route, a `cards` verb, an MCP tool, and firing the already-defined-but-unused artifact_added event constant. Doing it also retires the single largest built-but-dark capability in the repo (ROADMAP §4 / card dafd0873), converting sunk cost into shipped value. Keeping all four surfaces (HTTP/CLI/MCP/event) in lockstep is a one-session job precisely because the contract is already singular.
- **Events Step 4 — durable outbox/tailer delivery substrate** — This is the north-star move. Step 3 condition events (status_timeout, card_idle, card_blocked/unblocked, the tickless deadline scheduler, persist:true escalation) are fully built and firing, but delivery is still best-effort in-process SSE with a real commit-then-crash-before-dispatch gap. Until a durable cursor + dead-letter outbox exists, the entire large events investment carries engine-shaped complexity with none of the external-consumption payoff that justifies it philosophically. Landing the outbox is the explicitly-designed next milestone (marked [future] by intent, not neglect) and is the structural prerequisite for every downstream consumer.
- **Webhook delivery kind + /v1/subscribers status surface** — Built directly on the Step-4 outbox, a webhook delivery kind is what finally makes the events engine externally composable in a way that satisfies the 'resist anything expressible as `cards events stream` plus a script' test — because now the core delivers conditions outward and the reaction genuinely lives in an independent process (principle 6). A /v1/subscribers surface makes the fan-out observable and debuggable. Sequenced correctly this is the second half of the north star and the concrete proof of the composition thesis; it should follow, not precede, the durable substrate so deliveries are backed by the outbox's retry/dead-letter guarantees.
- **Dogfood this repo's own backlog on a live cards board** — The project's thesis is that agents and humans coordinate on typed cards, yet its own planning runs entirely on markdown (ROADMAP/NOTES/action-plan) with a 0-byte root work-cards.db and both live instances serving picraft — so the many card IDs cross-referenced in docs point at a board absent from this checkout. This gap is the likely root cause of the recent cross-facet misread (a facet read the historical debt ledger as current state; a live board would have made status unambiguous). Standing up a real board seeded from ROADMAP is a modest, self-contained step that exercises the full HTTP/CLI/MCP/event stack against the maintainers' own workflow.

## Appendix C — review feedback incorporated (by the Fable revise)

**design-ux**
- [blocker] Phase 2 does not close the human evidence loop. Its stated goal is 'humans, scripts, and agents can post an artifact (log, diff, screenshot) onto a card,' but every step targets HTTP/CLI/MCP only. The product has a real human surface (internal/httpapi/templates/card_detail.html, /ui/cards/{id}), and that template renders NO comments, links, or artifacts today. So a human uploads a screenshot and cannot see it anywhere in the browser — the loop closes for agents/API consumers and stays open for the human. A screenshot you can only GET as raw bytes over HTTP is not shipped user value for a human. → Add a Phase 2 step that renders attachments on card_detail (inline thumbnail for images, download link + MIME/size for others), and add artifact_added to the board's SSE type filter (ui.go boardSSETypes()) so an attached artifact appears on the live board without reload. Make the Phase 2 demo include 'attach a screenshot and see it on the card in the browser,' not just byte-identical GET.
- [major] The plan is blind to the existing /ui web surface across all five phases — the single human-facing surface in a product whose thesis is 'agents AND humans coordinate on typed cards' receives zero attention, while every phase and every demo serves API/CLI/MCP/agent consumers. This is the core design/UX gap: 'visible user value' is asserted but the human's visual surface is never touched or demoed. → Make the web UI a first-class consumer in each phase's exit criteria and demo where it applies (attachments rendered in Phase 2, board dogfooded in Phase 3, live-board integrity in Phase 4, subscriber health surfaced in Phase 5). At minimum, name /ui explicitly so it stops being an invisible fourth surface that silently drifts.
- [major] Phase 3 dogfoods the 'live board' but excludes the actual visual board. There is a real board at /ui/boards/{id}; the phase runs the daily loop only through CLI/MCP/JSONL and captures friction only from those surfaces. That deliberately skips exactly where human-coordination UX friction lives — the web board and card views — for a phase whose whole point is validating the human+agent coordination thesis. The 'live-drive in front of the room' demo is also far weaker as a terminal session than on the real board. → Run the dogfooding loop through /ui as well as CLI/MCP; have the friction log cover the web board/card-detail experience; and drive the demo on the actual /ui board (with the Phase-2 attachment visibly appearing) rather than a terminal-only walkthrough.
- [major] Phase 4's async tailer changes SSE latency/ordering, and the live web board depends on SSE directly — board.html opens an EventSource on /v1/events/stream and re-renders on mutation events. The regression plan names only temporal_test.go and SSE 'timing' tests; it never mentions the human live-board re-render behavior, which can visibly regress (missed updates, out-of-order badges, stale columns) under the new async path. → Add an explicit Phase 4 acceptance criterion that the live /ui board still re-renders correctly and in order under the async tailer (a browser/integration check on EventSource-driven updates), alongside the temporal/SSE unit tests.
- [minor] Phase 1's demo proves correctness, not value. 'Suite green + fault-injection test + git status clean + a one-line ledger diff' is an engineer's demo; it demonstrates nothing a user or operator would recognize as value, in a phase that (with Phase 4) delivers no visible user value at all. The lens question 'demos that prove value' fails here. → Reframe the Phase 1 demo around the averted user-facing consequence: show an operation that previously would have silently committed a card while losing its event, now visibly rejected — i.e., 'here is the data-integrity failure a user would never have known about, and here it is caught.' Make the stakes legible, not just the test bar green.
- [minor] Phase 5 exposes subscriber/delivery/dead-letter health as JSON only (GET /v1/subscribers). For an operator, retry counts, last error, and dead-letter state buried in a raw JSON endpoint is poor UX — especially when a visual operational surface already exists (/ui/breaches). The one operationally-critical, human-monitored state in the sprint has no human view. → Either add a minimal /ui view for subscriber/delivery/dead-letter health (mirroring the breaches page), or explicitly record 'JSON-only, no operator UI' as a known, accepted UX gap with a follow-up — don't leave it implicit.

**arch-data**
- [blocker] Domain-concept collision on 'Subscriber'. `core.Subscriber` already exists (bus.go:50) as an ephemeral in-process bus listener: {ID int64, Filter, Ch chan}. Phase 4/5 introduce a *durable* 'Subscriber' entity (subscribers.md RFC, /v1/subscribers, subscriptions table, cursor + dead-letter). These are different species — the RFC's premise that SSE Last-Event-ID is 'a client-held cursor of the same species' does not hold for the existing struct, which has no cursor and no durability. Shipping both under one name guarantees ongoing confusion in code, tables, and the REST surface. → In the Phase-4 RFC, explicitly reconcile the name before any code: either rename the durable entity (e.g. Consumer/Delivery/Endpoint) or rename the ephemeral bus struct (e.g. BusListener). Define the mapping from the existing ephemeral `core.Subscriber` to the durable model rather than asserting they are the same species.
- [blocker] Ephemeral conditions are structurally undeliverable to durable/webhook consumers — a hidden coupling the plan never states. The tailer reads the events *table*; but condition events default to the Signal path (events.go:84 — dispatch only, no Append), so status_timeout, card_idle, wip_*, lane_*, card_blocked never enter the log. Phase 4's demo (replay a card_idle from a cursor) and Phase 5's demo (status_timeout webhook surviving restart) are impossible unless those types are escalated to persist:true. Worse, PersistConditions is documented as startup-only ('Configure once at startup, before emission', events.go:92), yet a runtime-mutable /v1/subscribers subscribing to an ephemeral type would have to mutate that global config at runtime and re-arm the MonitorScheduler (which keys arming off IsPersisted, monitor.go:170). → Make the persist coupling a first-class RFC decision: registering a durable/webhook subscriber for an ephemeral condition type must either auto-escalate that type to durable (and the plan must resolve how that interacts with the startup-only PersistConditions invariant and MonitorScheduler arming) or be rejected at registration. Document per-type deliverability so a Subscriber.filter over event types is not silently a no-op for half the catalog.
- [blocker] mark-then-append atomicity gap defeats the outbox's core promise on the exact path it demos. In fireOne (monitor.go:340-349) MarkConditionFired commits in one transaction, then emitter.Condition→Emit→log.Append runs in a *separate* transaction. A crash between them permanently loses the event (never appended) AND marks it fired (never re-fires). The durable outbox cannot recover this — the gap is upstream of the log, so no cursor replay helps. Phase 4's 'stops being drop-on-crash / kill -9 mid-dispatch and replay card_idle' claim is false for escalated conditions until mark and append are made atomic. → Add to Phase 4 (or Phase 1 hardening): for persist:true conditions, write the fired-marker and the durable event append in one transaction (or append-then-mark with idempotent replay), so the condition_marks row and the log row commit together. Call this out as a correctness prerequisite for the outbox, not a Phase-4 incidental.
- [major] Phase 3's 'SQLite is a derived/rebuildable artifact' contradicts Phase 1 and orphans all delivery state. The append-only event journal (Phase 1: 'ground truth every downstream consumer trusts'), condition_marks, and the Phase 4/5 cursor / dead-letter / subscriptions tables live *only* in SQLite and are NOT derivable from a card-state JSONL export. Rebuilding the DB from the committed JSONL — the whole point of Phase 3 — wipes event history and all durable-delivery bookkeeping. 'SQLite is derived' is only coherent for current card state, not for history or delivery state. → Scope the Phase-3 export explicitly: JSONL is authoritative for card definitions + current card state only; the event journal, condition_marks, cursors, dead-letters, and subscriptions remain SQLite-owned and are never reconstructed from the export. State that rebuild-from-JSONL is a card-state operation that does not reconstitute history/delivery, so Phase 4/5 do not build durable state on a substrate Phase 3 declares disposable.
- [major] Tailer republish vs. existing synchronous dispatch: double-delivery or a broken observer contract. Emit already publishes to the bus and observers synchronously at commit (events.go:171-184); the hook supervisor is a live bus subscriber with an empty filter (hooks.go:65). A Phase-4 tailer that also 'republishes to bus/observers' from the log would deliver every persisted event twice to bus subscribers (SSE, hooks). Avoiding that requires re-routing SSE/observers to pull-from-cursor, which breaks the documented 'observers notified synchronously for every dispatched event' contract and changes hook-firing timing. The relationship between synchronous Emit-dispatch and async tailer-dispatch is left undefined. → Pin the dispatch topology in the RFC before Phase 4 coding: decide whether the tailer feeds only *new* durable consumers (bus/observers stay on the synchronous path, no republish) or replaces synchronous dispatch wholesale (and then re-specify the EventObserver/hook synchrony contract). Do not leave 'republishes to bus/observers' as an implementation detail.
- [major] Phase 1 Step 1's headline fix appears already satisfied at HEAD, which undercuts the foundation-first sequencing rationale. Current ClaimAtomic (sqlite.go ~643) returns and rolls back on both event-insert (execEventInsert) and FTS (upsertFTS) failure, and builds events via the shared core.OwnerChanged/StatusChanged constructors (Version:1 via CardEvent), not hand-rolled Version:0 literals. The DEBT-01/02/30/17 description in the plan does not match the code. → Re-verify DEBT-01/02/30/17 against HEAD before scheduling the work. If already fixed, either drop the step or re-anchor Phase 1's 'harden before layering' argument on a real remaining gap (e.g. the mark-then-append atomicity above, or DEBT-06 SSE replay), so the sequencing justification stands on something true.

**reliability**
- [blocker] Phase 3 demotes SQLite to a "derived/rebuildable" artifact reconstructed from the committed JSONL export, but (a) the export path serializes cards, not the events table (see exportJSONL/GetCard, DEBT-10), and (b) Phase 4 puts the durable outbox cursors and dead-letter records in that same SQLite DB. So a rebuild from JSONL silently destroys the event log and all delivery/dead-letter state. This directly contradicts Phase 1's own premise that the events table is the durable ground truth every consumer trusts, and Phase 4's at-least-once-across-restart guarantee. → Reconcile the two framings explicitly before either phase starts. Either scope Phase 3's "canonical JSONL" to definitions/card-state only while declaring the events table + cursor/dead-letter tables as authoritative, non-rebuildable durable state (not derived), or make the export/import round-trip events too. State in an exit criterion that rebuilding the DB must never drop event history or outbox delivery state.
- [major] Phase 1 Step 1's premise is stale. The current ClaimAtomic (internal/sqlite/sqlite.go ~700-720) already uses core.OwnerChanged/core.StatusChanged (no hand-rolled Version:0 events) and already returns/rolls back on execEventInsert and upsertFTS failure, with code comments to that effect. DEBT-01/30's cited lines (445-456) no longer match the code. The sprint sequences everything "foundation-first" behind a foundation that is largely already built, and would send a dev to re-fix fixed code. → Re-scope Phase 1 Step 1 against live code, not the ledger. Confirm what actually remains (e.g. DEBT-02 scanCard error masking, the non-ClaimAtomic swallowed-error sites in service.go AddLink/AddComment DEBT-03) and target those; drop the already-done ClaimAtomic version/rollback work or reduce it to a regression test that pins the existing behavior.
- [major] The plan is built on a debt ledger it simultaneously admits is stale. Phase 1 Step 3 corrects exactly one stale entry (DEBT-57, artifacts.Manager) but the same staleness invalidates Phase 1 Step 1 (ClaimAtomic) and part of Step 2 (DEBT-29 supervisor lifecycle is already partly handled: serve.go ties the supervisor ctx to ListenAndServe via defer cancel()). Reconciliation is sequenced third, after the fix steps whose scoping depends on it. → Move ledger/inventory/index.md reconciliation to the FIRST step of Phase 1 and re-derive every downstream step's scope from verified live code. Treat any ledger line:number reference as unverified until checked against the current file.
- [major] The go/no-go decision for the XL outbox exists only as risk-section prose. Phase 4 hard-dependsOn Phase 3 and the sprint theme commits to building the outbox regardless, so the "revisit before committing Phase 4" gate has no teeth: no defined signal threshold, no branch in the phase structure, no exit criterion that can read "no-go". → Make the go/no-go an explicit gate artifact from Phase 3 with a concrete, pre-registered criterion (e.g. measured dropped-event rate / classes of events lost across an induced crash that the team actually needs). Define what the sprint does if the answer is no-go (which later phases are cut).
- [major] Operational scope risk: five phases including an XL (outbox) and an L (webhooks) plus real core work in Phase 2 (Service.AddArtifact interacting with optimistic-concurrency versioning) in a single sprint. Durable-delivery code rushed under end-of-sprint pressure is exactly where crash-safety and ordering bugs hide, and the plan itself names subscriber-model divergence as its top design risk. → Split the durable-delivery work off. Land Phases 1-3 (+ the SUBSCRIBERS RFC) as one sprint; make the outbox+webhooks (Phases 4-5) a separate sprint gated on the Phase 3 signal and the agreed RFC. This also lets the RFC be reviewed cold rather than under coding pressure.
- [major] /v1/subscribers ships a runtime-registrable, arbitrary-outbound-URL entity (the first runtime-mutable, extension-like object in an otherwise file-declared extension model) with SSRF/exfiltration mitigation deferred to "a documented trusted-network assumption" rather than an enforced control. A documented assumption is not a failure-mode control. → Require an actually-enforced default-deny outbound allowlist (host/CIDR) as a shipping exit criterion for Phase 5, not just an RFC note. If that can't land, do not expose runtime registration this sprint; keep webhook subscribers file-declared like every other extension until the allowlist exists.

## Appendix D — external review of v2, incorporated in v3

An outside review of v2 (verified against HEAD) drove the v3 restructure:

1. **Explicit two-sprint split** — adopted. v2 kept one document with a gate;
   v3 names Sprint A (verify + attachments + dogfood + RFC) and Sprint B
   (outbox + webhooks, gated). The XL work is no longer schedule-gravity
   inside the same sprint.
2. **RFC moved to the end of Sprint A** — adopted; it lands regardless of the
   verdict and is written cold, in parallel with the dogfood session.
3. **Phase 1 un-bundled** — adopted. Reconciliation (S), fireOne atomicity
   (M-with-risk), and the drain convention (S) each get their own phase and
   exit criteria.
4. **/ui render first in the attachments work** — adopted, with a refinement
   the review missed: rendering existing comments/links/artifact metadata on
   card_detail.html needs no upload path at all and ships on day one. The
   pin-semantics contract test is kept (review suggested demoting it) but no
   longer gates the visible render.
5. **Phase 3 split into (a) JSONL canonicalization, (b) doc-id CI check,
   (c) time-boxed dogfooding** — adopted; (c) is time-boxed to one working
   session with the verdict as exit.
6. **Concrete binary go/no-go criterion** — adopted in *shape* but corrected in
   substance: the review's proposed test (fired persist:true events absent
   from the log after SIGKILL) tests the layer the fireOne fix closes, and its
   direction was inverted relative to v2's needs-question. v3 pre-registers a
   two-part gate: a foundation gate (log integrity, binary, must pass) and a
   needs gate (consumer-delivery layer, decides whether the outbox is built).
7. **Reject-at-registration promoted to the RFC's default answer** for
   ephemeral-condition deliverability — adopted (v2 already named it the safe
   fallback; v3 makes it the default, auto-escalation a future extension).
8. **Appendices moved out of the plan body** — this file.

## Pitch

An internal-substrate sprint, framed honestly: no board viewer or CLI user sees a new feature. What it ships is (1) a planning ledger that tells the truth about code, with the recurring drift class converted into a behavior-asserting CI test, and (2) the sanctioned SQLite reader pool — or, if measurement says reads aren't the pain, the write-hold-time reduction that is — so the multi-agent concurrency the last sprint enabled stops queueing every read behind one connection. The payoff is perceptible only under concurrent load, so the closing demo is measured and felt through transports users actually touch (MCP/HTTP UI), not a microbenchmark table. Auth stays a frozen design decision closed out on the board, not code built here.

## P2 — Isolated shared-cache test harness + measured file-WAL baseline

**Goal:** Build the one seam the pool needs — a per-test-isolated, multi-connection-capable in-memory harness — and replace the mis-framed 'connection-bound vs write-hold' spike with the real question: does read latency observably degrade under realistic concurrent load today, measured on a file-backed WAL DB through a real transport? Starts immediately; no dependency on P1.

**Steps:**

1. Extract a single shared test-store constructor (internal/sqlite/sqlitetest or similar) that mints a UNIQUE shared-cache name per Open — file:test_<uuid>?mode=memory&cache=shared — and holds a keep-alive connection for the store's lifetime (a shared-cache memory DB is dropped when its last connection closes). This gives per-test isolation under parallel `go test` AND the >1-connection topology P3 requires, replacing the MaxOpenConns(1) crutch. Migrate all 29 direct :memory: test call sites (recounted from the plan's earlier estimate of 20): 26 open a Store via sqlite.Open across internal/core, internal/mcp, internal/cli, internal/httpapi, and cmd/, plus 3 that open a raw *sql.DB via sql.Open in internal/sqlite tests (statussince_test.go, eventscope_test.go) — route those through a raw-db variant of the same constructor so there is exactly one code path.
   - **Outcome:** All in-memory tests open through one constructor; each test gets an isolated named DB that stays coherent with multiple connections; go test ./... (including -race, parallel) stays green.
   - **Touches:** new internal/sqlite/sqlitetest helper; 29 *_test.go call sites (26 Store, 3 raw-db)
2. Run the baseline measurement against a FILE-backed WAL DB in a tempdir (matching the production Open path — :memory: has no fsync and would fake the verdict), driven through a transport users touch (HTTP ListCards, optionally MCP). State the load profile up front (e.g. 8 concurrent readers at a sustained write rate resembling dogfooding traffic) and record p50/p95 read latency. Decision rule, written before running: (a) reads degrade observably under write load → proceed to P3 pool (the conn cap at sqlite.go:44 is the known serializer); (b) reads are fine but writes stall → P3's alternate scope: reduce write-tx hold time (FTS upsert + event insert in UpdateCard at sqlite.go:587); (c) nothing observable → park P3 with the evidence recorded on the canonical card.
   - **Outcome:** A recorded p50/p95 baseline at a stated load profile, and an explicit a/b/c decision that determines P3's scope.
   - **Touches:** internal/sqlite benchmark test (kept, file-WAL-backed)

**Demo:** Verification (not a user demo): the one-constructor harness with all 29 migrated call sites and race-clean parallel tests, plus the baseline table (load profile, p50/p95 read latency under write load on file+WAL) and the written a/b/c verdict.

**Exit criteria:**

- Exactly one code path opens test DBs (Store and raw-db variants of the one constructor); unique-name-per-Open isolation and keep-alive lifetime are verified under parallel go test -race
- Baseline measured on file-backed WAL through a real transport, with p50/p95 recorded and the pre-committed a/b/c decision rule applied

## P3 — Reader pool (or write-hold reduction), proven on file+WAL

**Goal:** Ship whichever concurrency fix P2's measurement selected. Primary scope: a reader pool with its own deferred/read-only DSN so reads stop queueing behind the single writer, with the write path's _txlock=immediate discipline untouched. Alternate scope (P2 verdict b): shrink UpdateCard's write-tx hold time instead. Either way the phase ships a measured, felt improvement — the sprint does not collapse to hygiene.

**Depends on:** P2

**Steps:**

1. Split Open into two handles with distinct DSNs: writer keeps the current DSN (_txlock=immediate, MaxOpenConns(1)); reader pool gets a DSN WITHOUT _txlock=immediate, opened read-only (mode=ro or query_only pragma) so a misrouted write fails loudly. Sequence: open writer → Ping → Init/migrate (establishes WAL) → only then construct the reader pool with matching busy_timeout/foreign_keys pragmas. Add a pool-size knob (env/config) where size 1 restores today's serialized behavior as a runtime escape hatch. Document in the core.Store comment: migrations are writer-only; readers see the last committed WAL snapshot; read-your-own-writes requires the writer handle; the cross-process immediate-tx discipline (serve + serverless CLI on one file) is unchanged by the in-process pool.
   - **Outcome:** Two handles with correct DSNs and init ordering; a misrouted write through the pool errors; pool size 1 reproduces current behavior.
   - **Touches:** internal/sqlite/sqlite.go (Open, handle fields), internal/core/store.go doc comment
2. Route every Store method via a complete audit table — every method appears in exactly one column (exit criterion). Readers on the pool: ListCards, CountCards, GetCard, GetCardsByShortID, ListLinks, AllLinks, Blockers, BlockingDependents, ListComments, comment counts, EventQuery List/Page, ListUsers, plus the advisory check-then-act reads ConditionFired (sqlite.go:1050) and GetIdempotency (sqlite.go:1137) — safe on the pool ONLY because the authoritative guard is the in-tx INSERT-OR-IGNORE rowcount / writer-side upsert; note this in the table. Writers and read-then-CAS stay on the writer: Insert/Update/DeleteCard, ClaimAtomic, links/comments writes, event Append, idempotency writes, user upserts, migrations. Audit call SEQUENCES too: any handler that writes then re-reads to render the fresh card must read through the writer — give reader helpers a queryer interface (pool or tx) so query code isn't forked. Note in the audit: UpdateCard's conflict re-read inside its own immediate tx makes stale pool GetCard yield a normal version_conflict, no new hazard.
   - **Outcome:** Complete two-column audit committed with the change; read-your-own-writes paths provably on the writer; queryer interface avoids duplicated query logic.
   - **Touches:** internal/sqlite/sqlite.go (all Store methods), internal/httpapi handlers with write-then-read sequences
3. Prove it on file+WAL, not memory: (1) a regression test on a tempdir WAL DB where N readers return while a writer holds the write lock, race-clean; (2) a freshness test that creates a card through the normal handler path and immediately re-reads it, asserting the fresh version; (3) re-run the P2 benchmark for the after-numbers. ALTERNATE SCOPE if P2 chose (b): instead of the pool, reduce write-tx hold time (move FTS upsert/event-insert work out of the critical section where safe) and prove it with the same before/after benchmark; the harness, audit table, and doc-comment work still land.
   - **Outcome:** Concurrency and freshness tests pass race-clean on the production DB configuration; measured p50/p95 improvement over the P2 baseline.
   - **Touches:** internal/sqlite/*_test.go (file-WAL-backed), internal/httpapi test

**Demo:** A felt before/after through a user-touched transport: two dogfooding agents hammering the board (sustained writes via MCP/HTTP) while the /ui board and MCP ListCards are exercised — responsive in the after, visibly queueing in the before (pool knob set to 1) — alongside the p50/p95 table. go test -race ./... green.

**Exit criteria:**

- Reader DSN has no _txlock=immediate and is read-only; a misrouted write fails loudly (asserted in a test)
- Audit table is complete — every Store method classified into exactly one column, sequences included, advisory reads annotated
- Concurrent-reader and read-your-own-writes freshness tests pass race-clean against file+WAL
- Measured p50/p95 read-under-write improvement over the P2 baseline (or, alternate scope, write-hold improvement), via a transport users touch

## Risks & de-risking

- Misclassifying a Store method or call sequence as pool-safe reintroduces either SQLITE_BUSY_SNAPSHOT-class failures or stale read-your-own-writes — mitigated by the complete audit table (every method in one column), the queryer interface, and the handler-path freshness test, but the audit's completeness is itself the failure mode to watch
- modernc.org/sqlite's shared-cache named-memory-DB semantics (unique name per Open + keep-alive lifetime) must behave as documented; verify with a focused test before migrating all 29 call sites, since parallel go test would surface leakage as flaky cross-test state
- P2's measurement may select the alternate scope (write-hold reduction) or park — that is a designed outcome, not a sprint failure; the fallback is named and the harness/audit/doc work lands regardless
- The felt demo depends on generating enough concurrent load to make the before-case visibly queue; if dogfooding-scale load can't reproduce perceptible pain, report the honest p50/p95 numbers and say so rather than staging a misleading demo
- The auth closeout in P1 can balloon if treated as a fresh design pass; the freeze note limits reopening — keep it review + crosslink + card hygiene, S-sized
- Two DSNs mean pragma drift is now possible (a pragma added to one handle and not the other); the Open-sequencing step centralizes pragma construction to prevent this, but reviewers should check it in the diff

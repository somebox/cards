## Appendix A — project state survey

Cards is a Go-based typed-card/kanban engine that just reached its first tagged
release, v0.1.0 (2026-07-06). The shippable baseline is coherent and green:
typed cards + append-only event log, a 9-condition reactive-coordination engine
(WIP limits, lane conditions, blocked/unblocked, timeout/idle deadlines), a
tickless scheduler, resumable SSE, and content-addressed attachments wired end-
to-end across HTTP/UI/CLI/MCP surfaces. The release was the payoff of two
disciplined, back-to-back efforts: a "Events seam" rollout (steps 1a-3e) that
built the condition engine seam-by-seam with golden fixtures, and a formal
7-phase "Sprint A" debt-review that reconciled a 57-item ledger against HEAD and
fixed essentially all high/medium code-correctness debt (the DEBT-01 ClaimAtomic
error-swallowing cluster, a persist:true crash-safety gap, hook-supervisor
graceful drain, and a CLI machine-contract cluster) each pinned by named tests.
The full suite passes across all 15 packages with only one environment-guard
skip and zero in-code TODO/FIXME comments — the team deliberately tracks all
remaining work on its own dogfooded board (96 cards: 79 done, 10 todo, 5
backlog, 1 review, 1 in_progress) rather than in code or docs. Post-release
momentum has shifted to (1) making the board itself portable and durable via
scripts/board.sh git export/import, and (2) an in-flight UI/UX polish push
(uncommitted changes to render.go, card_partial.html, style.css, README plus a
broad docs restructuring). The one large feature area deliberately NOT built —
durable outbox/webhooks ("Sprint B") — was gated behind a pre-registered go/no-
go verdict (NO-GO: no real consumer was observed losing events) with the
subscribers.md RFC preserved cold for a future trigger. Net: a healthy, well-
instrumented project that just cleared its debt, shipped a baseline, and is
pivoting from core-engine hardening to frontend polish and workflow tooling,
with a thin, actively-groomed remaining queue.

## Appendix B — vision alignment

Cards is deliberately a small kernel for typed-card coordination, not a
framework or a Jira/workflow-automation platform. Its ten principles pull in one
direction: a core that "grows reluctantly" (fixed 10-field catalog, hooks-not-
engines, extensions-not-plugins), boring tech (SQLite/JSON-YAML/HTTP-
SSE/subprocess), local-first single-tenant "YOLO defaults" with auth/authz
pushed to the host, files where humans review and SQLite where machines query,
and above all "stable, documented contracts meant to outlive any specific
implementation." The stated north star (NOTES theme, D15) is the agent
coordination loop: introspect -> take-next -> work -> append evidence ->
transition -> comment. The web board is explicitly "only one view over the same
API," not the product. Success is being "obviously small before obviously
featureful."

Recent momentum is strongly vision-consistent where it counts. The Sprint A
debt-review (crash-safe append, ClaimAtomic error surfacing, graceful hook
drain, CLI machine-contract cluster, each pinned by named tests) directly serves
principles #8/#9 (stable contracts, fail loudly) and hardens the coordination
loop the whole product exists to run. The outbox/webhooks NO-GO is a textbook
expression of "core grows reluctantly" and "resist anything expressible as
events-stream plus a script" — refusing to build durable delivery infrastructure
ahead of an observed consumer losing events is exactly the restraint the
philosophy demands. Attachments shipped with the right scope
(path/json/yaml/command field types deliberately dropped to extension territory;
only artifact/link-to-bytes kept), honoring the small-catalog rule. board.sh git
export/import embodies "files where they help": definitions committed, live
SQLite gitignored, portable snapshot diffing cleanly. For the USER (the
maintainer dogfooding this), the payoff is real: a green, contract-honest v0.1.0
baseline whose moat is smallness and stability, not feature count. That moat is
intact.

**Tensions**
- UI gravity vs. 'only one view.' 8 of 10 todo cards are frontend polish (modal
spacing, board-settings editor, new-card modal), and uncommitted work spans
render.go/card_partial.html/style.css. The philosophy is emphatic that the board
'is useful, but it is only one view over the same API.' Post-release energy
flowing to the most visible surface rather than the load-bearing one
(agent/CLI/MCP contracts) is the single clearest drift vector — it risks the
product's center of gravity sliding from coordination kernel toward kanban app.
- Human polish leapfrogging agent ergonomics — a misalignment with the stated
theme. The short-id resolution inconsistency (short ids resolve for get/list but
NOT patch/comment/attach) and the workspace init/attach-unreachable friction sit
in backlog/todo while modal spacing advances. These bugs live squarely on the
agent coordination loop and violate #9 (fail loudly, self-correct): an agent
gets silent/asymmetric behavior on the exact verbs it drives. Trimming 'to what
serves the agent loop' (NOTES theme) argues these outrank any UI card.
- Contract-honesty drift needing a product decision, not just a fix.
DEBT-40/41/53: SPEC/ARCHITECTURE/DEVELOPER-REFERENCE claim workspace/card-
type/board defs accept JSON or YAML, but config.go parses only JSON. This
directly contradicts principle #8 (contracts meant to outlive the
implementation) and the README's own framing. Docs-vs-code divergence in the
normative contract is a vision violation, not ordinary tech debt — 'correct the
docs vs. implement YAML' should be decided before the contract calcifies wrong.
- Release credibility gap. DEBT-54 (CI matrix tests Go 1.25 against go.mod go
1.26.4 — build will fail) and DEBT-55 (golangci errcheck still references the
old module path github.com/foz/work-cards) undercut a just-tagged v0.1.0.
'Boring tech' and 'stable contracts' imply CI should be green and honest about
what it builds; a release whose CI can't build its own declared toolchain erodes
the baseline's trust.
- Half-in-core orphans violate 'small core.' The View type exists in
internal/core with no route/CLI/service wiring — the philosophy says design it
(saved views over the existing query DSL is genuinely aligned) or explicitly
drop it, not leave it dangling. Similarly the hook-payload contract ambiguities
(board_ids, service-kind supervision) are documented-but-unemitted seams that
quietly widen the gap between index.md and reality.
- Dogfooding irony as a weak signal. The lone in_progress card has sat >1 week
with 2 of 3 WIP slots open, and P2 backlog cards are 11+ days stale — the
product's own card_idle/status_timeout conditions would flag exactly this. Not a
vision breach, but the maintainer's board is drifting from the reactive-
coordination discipline the engine is built to enforce.
- Docs-site + restructuring risk. The GH-Pages microsite is entirely unbuilt
scaffolding and a broad ~24-file docs churn is in flight; good for adoption but
a proliferation risk against principle #10's spirit — more surface to keep
contract-honest, right when the JSON/YAML drift shows honesty is already
slipping.

**North star for this sprint**

Recommit the near-term queue to the agent coordination loop and contract honesty
over human-facing UI polish. Concretely: (1) fix short-id parity across ALL
verbs (patch/comment/attach), and resolve the workspace-init/attach-unreachable
friction so the loop works out of the box; (2) make the normative contract true
again by deciding and closing the JSON/YAML docs-vs-code drift and the stale CI
toolchain/module-path issues. This is the most vision-advancing direction
because the durable, differentiated product is the small typed-card substrate
with stable contracts that agents and scripts drive — 'only one view' UI polish
does not advance that, whereas frictionless, honest contracts are the moat the
philosophy names. Ship the UI sprint after, as the second view it is.

## Appendix C — candidates considered

### `short-id-write-verb-parity` — Short-id parity across all write verbs (patch / comment / append / attach)

Verified in the tree: PatchCard (service.go:695), AppendEntry (:980) and
AddComment (:1191) call the raw full-id-only s.getCard, while AttachArtifact
(:849) already uses s.ResolveCard, and get/list resolve short ids too. The fix
is narrow and mechanical — route the write verbs through the existing
ResolveCard (which already returns *AmbiguousIDError for humans/agents to
disambiguate) instead of getCard. This is small-surface, foundation-first: it
makes the Service layer's id-resolution contract uniform rather than verb-
dependent.

**User value:** An agent or CLI user who successfully did 'cards get 3f2a9c1b'
gets a silent/asymmetric failure when they try 'cards patch/comment 3f2a9c1b'
with the same short id — the single worst papercut on the
introspect->work->append->transition loop. Uniform resolution removes a class of
confusing failures on the verbs the product exists to run.
**Alignment:** Directly serves the north star (agent coordination loop first)
and principle #9 (fail loudly, self-correct, no silent asymmetry). It is the
highest-leverage, lowest-cost item that recommits the queue to the loop over UI
polish.

### `loop-works-out-of-the-box` — Make the coordination loop work out-of-the-box: fix workspace init/target friction and ship a starter artifact field

Two coupled friction points block a clean first run of the loop: 'cards init X'
scaffolds X/.cards but --workspace/$CARDS_WORKSPACE expect the .cards dir itself
(silent empty-workspace opens), and no shipped card type declares an 'artifact'
field, so the fully-wired 'cards attach' verb is unreachable from a fresh
install. Fixing init/target resolution (accept either the parent or the .cards
dir, and fail loudly on an empty workspace) plus adding an artifact field to a
starter type turns a built-but-hidden capability on.

**User value:** A new maintainer or agent can go from 'cards init' to a working,
attach-capable board without hitting a silent empty-open or discovering that a
shipped feature has no reachable entry point. It converts the already-paid-for
attachments backend into usable value.
**Alignment:** Serves the loop-out-of-the-box north star and 'fail loudly' (#9):
silent empty-workspace opens are exactly the failure mode the philosophy
forbids. Activating attachments via a starter field honors 'files where humans
review' without growing the core.

### `json-yaml-contract-decision` — Close the JSON/YAML contract drift with an explicit product decision (correct docs vs. implement YAML)

Confirmed: internal/config/config.go parses definitions with json.Unmarshal only
(lines 99/133/168) while SPEC/ARCHITECTURE/DEVELOPER-REFERENCE and the README
claim JSON-or-YAML for workspace/card-type/board defs (DEBT-40/41/53). This is a
normative-contract divergence, not ordinary debt — it must be decided before the
contract calcifies wrong. Cheapest honest path is likely to add a yaml.Unmarshal
fallback in the three parse sites (the yaml dependency already exists for
extensions), making docs true; the alternative is a doc correction. Either way,
decide and pin with a test.

**User value:** The maintainer authoring definitions by hand gets the YAML
ergonomics the docs promise (or docs that no longer lie). Contract honesty is
the product's stated moat — a false normative contract erodes exactly the trust
that a small, stable kernel sells.
**Alignment:** Principle #8 (stable, documented contracts meant to outlive the
implementation) and the 'files where humans review' bias toward YAML authoring.
Resolving this protects the just-tagged v0.1.0 baseline's credibility.

### `complete-attachments-and-ship-ui-sprint` — Ship the groomed UI/UX sprint, led by the browser attachment upload view

The artifacts backend is fully wired (content-addressed store, MIME sniffing,
path confinement, SSE thumbnails) but human upload is CLI/API-only — a drag-drop
multipart upload view is the last residual TODO on a shipped feature, not net-
new surface. Anchoring the already-partly-written UI sprint (card-modal
comments/entries, board-settings editor, new-board/new-card modals, spacing pass
— 8 of 10 todo cards, uncommitted work in render.go/card_partial.html/style.css)
on completing attachments makes the visible-surface push finish a built
capability rather than accrue pure polish.

**User value:** Humans reviewing a board get to attach and preview artifacts,
create boards, and edit settings without dropping to the CLI — the tangible
payoff of the post-release momentum, and the point where the web board becomes a
genuinely usable second view.
**Alignment:** Legitimately advances the product as 'only one view over the same
API' — sequenced after the loop/contract work per the north star, so UI gravity
completes a built feature instead of pulling the center of gravity toward being
a kanban app. Completing attachments respects the small-catalog rule (no new
field types).

## Appendix D — cross-cutting analysis (Fable, the hardest step)

**Foundations to tackle first**
- Centralize error mapping at the HTTP boundary before touching any verb: today
writeAPIError(core.AsError(err)) turns any non-*core.Error (including
*AmbiguousIDError) into a generic 500 'unknown error'. Either make ambiguity a
*core.Error variant (code 'ambiguous_id') so AsError handles it natively, or add
one shared writeServiceError helper used by all ~30 handler call sites in
internal/httpapi/api.go. This single change fixes the live DELETE bug, makes the
12-verb short-id conversion purely mechanical, and removes the copy-paste branch
every future handler would otherwise need.
- Introduce one Service-layer 'resolve card reference for write' helper
(ResolveCard-backed) and swap all 12 getCard call sites
(service.go:695,895,980,1023,1067,1098,1114,1156,1191,1228,1280,1320,1351 plus
History:1473) through it in one pass, rather than verb-by-verb. This makes 'card
reference = full id or short id' the universal Service contract, which every
future surface (MCP tools, bulk verbs, RPC) inherits for free.
- Add the artifact field to the shipped task card type
(internal/starter/assets/definitions/card-types/task.json) AND resolve the
starter-vs-examples/demo-workspace duplication in the same change (ideally
generate/sync the demo workspace from starter assets). This is the shared step-
zero for both 'loop-works-out-of-the-box' and 'complete-attachments-and-ship-ui-
sprint' — done once, deliberately, it unblocks both and sets the precedent for
how shipped defaults evolve.
- Decide the AddArtifact optimistic-concurrency question (version/CAS parameter)
BEFORE building the upload UI. It is the only mutation without a version check;
changing the service signature after a browser UI ships is far more expensive
than deciding now (fix it, or explicitly document last-write-wins for artifact
fields).
- Build one shared 'refresh modal after a non-PATCH mutation' JS helper in
layout.html as part of the attachments UI, designed for reuse by the
comments/entries card and future repeating-field UI — the first consumer pays
for it, the next three get it free.
- Normalize workspace-path acceptance (project root or .cards child, with an
explicitly documented precedence rule) inside resolveWorkspaceDir only, with a
dedicated cmd/cards/workspace_test.go — so serve, direct CLI, and MCP entry
points all inherit git-style discovery from one tested function.

**Tech debt to clear**
- DEBT-54: CI matrix tests Go 1.25 against go.mod's go 1.26.4 — builds fail, so
no other work can land with confidence. Fix first, it is a one-line change.
- DEBT-55: .golangci.yml errcheck exclusion still references the old module path
github.com/foz/work-cards — lint is silently not covering what it claims. Also
one line.
- DEBT-40/41/53 (json-yaml-contract-decision): the investigation entry is a stub
('test' placeholders) — the real work is a product decision, not code. Recommend
deciding 'docs say JSON-only' (correct the SPEC/ARCHITECTURE/DEVELOPER-REFERENCE
claims) rather than implementing YAML parsing; it touches 4 files of docs vs a
new dependency and parser surface. Whatever the verdict, decide it early because
the large modified-docs set currently in the working tree risks re-encoding the

- Latent DELETE-on-ambiguous-short-id 500 bug (api.go:169-172 path through
AsError returning nil) — subsumed by the error-mapping centralization above; do

- Stale doc comment in internal/artifacts/artifacts.go ('No HTTP endpoint calls

- Test debt that gates the above: no dedicated tests for
resolveWorkspaceDir/findDotCards, and TestResolveCard_* covers only the read

extension supervision) — defer; not on the critical path for any current
candidate, but record the decision deadline before the next extensions-facing
release.

**Domain-model evolution**
- 'Card reference' as a first-class concept: promote id-resolution from a read-
path convenience to the universal contract — any place an id appears (URL path,
AddLink's embedded in.Target at service.go:1114, future bulk-op payloads)
resolves identically. This requires one explicit scoping decision now: do
embedded ids in write payloads (link targets) participate in short-id
resolution? Recommend yes, since the resolution helper becomes the single
extension point either way.
- Ambiguity as a modeled error, not a special case: fold AmbiguousIDError into
the core error taxonomy (a *core.Error with code 'ambiguous_id' carrying
candidates) so all transports (HTTP, CLI, MCP) render it uniformly without per-
handler knowledge.
- 'Workspace target' contract widening: --workspace/$CARDS_WORKSPACE accepts
either the project dir or its .cards child, mirroring init's positional arg and
git's repo discovery — a small public-contract change that must land atomically
with main.go usage text and cli.md.
- Shipped defaults as a maintained product surface: adding the artifact field to
task.json makes the starter set the 'canonical demonstrable' schema. Establish
the rule that examples/demo-workspace is derived from (or CI-checked against)
internal/starter/assets, so old-vs-new onboarding boards cannot silently fork.
- Uniform concurrency contract: 'every card mutation takes a version' should
become an invariant (AddArtifact is the sole exception today). Either close the
gap or explicitly document artifact fields as last-write-wins — the decision
itself is domain-model work.
- Single client-side mutation/refresh idiom: the UI currently has two fetch
patterns (save-form FormData, version-CAS PATCH) and is about to grow a third
(raw Blob POST). Consolidating around a small set of named idioms plus one
modal-refresh helper is the UI-layer equivalent of the Service-layer resolution
contract.

**Sequencing**
Phase 0 (hours): fix DEBT-54/55 so CI is green and lint is honest — nothing else
can be verified without this. Also make the JSON-vs-YAML docs decision now,
since the working tree already has ~25 modified docs files that would otherwise
re-encode the false claim. Phase 1 (the error/resolution foundation): centralize
AmbiguousIDError handling at the HTTP boundary (or fold it into core.Error),
THEN do the 12-site getCard→ResolveCard swap with a table-driven per-verb test —
order matters, because converting verbs first would convert today's wrong-but-
uniform 404s into 500s. This fully delivers short-id-write-verb-parity and fixes
the existing DELETE bug as a side effect. Phase 2 (the reachability foundation):
add the artifact field to starter task.json, sync/derive examples/demo-
workspace, and widen resolveWorkspaceDir with tests + doc updates — this
completes loop-works-out-of-the-box and is the explicit step-zero blocker for
the attachments UI. Phase 3 (decision gate): settle AddArtifact version/CAS
semantics before any upload UI exists, since retrofitting the signature after
browsers make races common is the expensive path. Phase 4: build the attachments
upload UI (raw Blob POST matching cmdAttach's wire contract, not multipart),
extracting the shared modal-refresh helper — which then unblocks the
comments/entries card and the remaining UI-sprint backlog as cheap followers
rather than independent efforts. Net effect: Phases 0-1 make every current and
future write verb cheaper; Phase 2 makes every onboarding/demo/docs effort
cheaper; Phases 3-4 make the remaining ~8 UI cards cheaper.

## Appendix E — review lenses (must-address counts)

### Lens: design-ux

- **[blocker]** Phase 4's upload demo ('drag a PNG onto it, watch it upload')
specifies zero interaction states. There is no drag-over drop-zone affordance,
no in-flight progress/loading indicator, no success confirmation, and — most
damaging — no client-side handling of the 32MiB cap or a server 400. The plan
notes the backend rejects oversize/multipart with a 400 but never designs what
the user sees when that happens: a drop that silently does nothing is a broken
experience, not a shipped feature. A 'genuinely-useful second view' cannot demo
a happy path only.
  Fix: Specify the full state machine for the upload control before building it:
(1) idle/empty affordance, (2) drag-over highlight on the drop target, (3)
uploading/progress, (4) success (artifact appears), (5) explicit error surface
reusing the modal's existing .alert element (card_modal.html already renders
{{.Error}} as an alert) for oversize (>32MiB, checked client-side before POST)
and server 400s. Add these paths to the Phase 4 demo and exit criteria.
- **[blocker]** Phase 4 is drag-drop-only, which excludes keyboard, touch, and
screen-reader users and is inconsistent with the rest of this UI. The existing
modal is deliberately keyboard-accessible (tabindex/in-place edit, a visually-
hidden AT label on the card type mark), so a drop-only upload regresses the
established a11y bar. Separately, HTML5 drag-and-drop is ALREADY the board's
gesture for moving cards between columns (layout.html:162-185); introducing
file-drop without scoping it invites gesture collision.
  Fix: Require a visible click-to-browse <input type=file> as the primary
control with drag-drop as an enhancement (not the reverse). State explicitly
that file-drop is scoped to the open modal, never the board card, so it cannot
collide with the column-move drag. Add 'keyboard/click upload works without
dragging' to Phase 4 exit criteria.
- **[major]** Phase 5 mislabels 4–5 distinct design problems as 'cheap
followers': in-modal comments/entries editing, a new-card modal, a new-board
creation flow, a board-settings editor, plus a spacing/polish pass — collapsed
into one phase with one chained demo. These are cheap on the API layer, not on
the design layer: each needs its own form design, validation, required-field
handling, and empty/error states (e.g. new-board with no cards, a rejected board
name). The single demo that chains all five hides that none of them has defined
failure or empty states.
  Fix: Split Phase 5 into separately-demoed deliverables (at minimum: modal
editing, card creation, board creation+settings) each with its own empty/error
state in its exit criteria. Drop the 'cheap followers' framing — they are
follower-sequenced, not low-effort.
- **[major]** The theme claims 'each phase delivers visible user value,' but
Phases 1 and 3 deliver contract/documentation value that is invisible on the
board. Phase 3 in particular is two product decisions plus a doc-comment fix. If
the sprint truncates after Phase 3, nothing an end user (on the board) can see
has shipped — the first board-visible change is gated behind three foundation
phases.
  Fix: Make the value framing honest by naming the audience per phase: Phases
1–2 serve the agent/CLI user (real, but not the board); Phases 4–5 serve the
board user. Then de-risk truncation by pulling one small board-visible win
earlier (e.g. the board-card artifact affordance from Phase 4 step 3, which is

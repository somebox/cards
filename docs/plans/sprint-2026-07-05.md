# Sprint plan — From detection to durable coordination: making the events engine externally composable

*Generated 2026-07-05 by the `sprint-plan` workflow — 19 agents, ~699,371 tokens, 212 tool calls. Discovery on Sonnet, cross-cutting strategic analysis (the hardest step) on Fable@high, synthesis/plan/review on Opus. Draft → 3-lens review (design/UX · architecture/data · reliability) → ready-for-dev refinement.*

## Theme

The reactive engine detects and emits, but reaction still lives in-core and dies on a crash. Two phases are honestly labeled enabling foundation (registry dispatch + graceful lifecycle; then a durable delivery substrate); the rest is user value. To flatten the value curve, the single most user-legible deliverable — attachments end-to-end — is pulled forward to run right after Phase 1 (its only dependency), so a tangible win lands second, not fourth. Marquee coordination value then stacks on the durable substrate: webhook delivery that survives commit-then-crash, made observable via a subscriber-status surface, and a first real external extension. Ordering is load-bearing: foundation before feature, and cursor/dead-letter/tailer semantics are co-designed as one frozen unit up front because that shape is the plan's own expensive-to-walk-back risk.

**North star:** Land Events Step-4 (durable outbox/tailer) and the webhook delivery kind on top of it. This is the single most vision-advancing direction because it converts the newly-built reactive engine from in-core detection into externally-composable coordination: durable, replayable outbound delivery is the seam that keeps 'hooks, not engines' honest (reaction lives in subscribers, not the kernel), realizes 'extensions over plugins,' and finally gives the unproven 'big composition' story a real integration surface for the deferred worked examples to hang on. For the USER it means coordination signals that survive a commit-then-crash and reach external systems reliably — the difference between a demo and something a team can depend on. Pair it with wiring attachments end-to-end as the contained user-facing completion that should not keep waiting behind engine work.

## Risks
- The cursor/dead-letter/tailer shape is the plan's expensive-to-walk-back decision; it is frozen in Phase 3 before Phase-4 webhooks depend on it — if the last-scanned/advance-past model is wrong, Phase 4 pays the rework.
- The generic last-scanned cursor is validated against only one real consumer (webhooks) this sprint; no second consumer (SSE-resume/priority-rank) proves the generalization — accepted residual risk.
- Making durable-consumer-on-ephemeral-condition a fatal Load error deliberately breaks the existing 'Warnings never block Load' contract; any config relying on non-fatal warnings will newly fail Load.
- Webhooks add the codebase's first outbound-network surface in a local-first/trusted-by-default design; the trust posture is documented but not enforced with authz (out of scope).
- The surface-matrix parity check is report-only until end of Phase 5; drift can accumulate silently until the gate flips green.

## Appendix B — candidates considered
- **Events Step-4 durable outbox/tailer + first-class webhook delivery kind** — This is the last unbuilt seam of an otherwise-complete engine (ROADMAP §5, epic card d416cec3 + 180e7621) and the direct enabler of the proposed webhook kind (§6, card a9f78958). Today dispatch is fire-after-commit: a crash between the SQLite commit and the bus fan-out silently drops a coordination signal, and only an observe-post-hoc shell hook can react (per §2). A durable-log-driven tailer with cursor replay + HMAC signing turns detection into reliable delivery. It builds cleanly on what already shipped (resumable SSE, /breaches, tombstone events) rather than adding new core surface, and it is the sequencing prerequisite for candidates 2 and 3 below — everything external subscribes through this seam. Ship the temporal-coverage fix for /breaches (status_timeout/card_idle, §5) alongside it since the tailer touches the same rebuild scans. _(user value: Coordination signals (WIP overflow, idle cards, deadline breaches) survive a commit-then-crash and reach external systems reliably with retry — the difference between a demo and a substrate a team or agent fleet can actually depend on. Webhooks give every non-Go consumer a zero-polling integration point.)_
- **Wire attachments end-to-end (ingest + serve + CLI/MCP)** — A contained, unusually cheap completion that is being outranked by less user-facing engine polish. The hard, risky part is already done and adversarially tested: internal/artifacts is a content-addressed store (SHA-256 dedup, MIME sniffing, symlink-safe confinement) and the artifact field type exists, with the local-vs-uri policy already shipped (0578312 / DEBT-57). What is missing is purely wiring (ROADMAP §4, card dafd0873): an ingest path (Manager.Put), a serve route (Resolve/Open with its confinement checks), write-time validation of the {uri,mime,size,sha256} metadata shape, an artifacts root wired into the server, and CLI/MCP verbs that emit the already-declared artifact_added event. No new subsystem, no design risk. _(user value: A user literally cannot attach a file today, even though 'posting links to artifacts' is a named core use case and other field types were deliberately dropped to keep this one. This closes a visible, felt hole in base functionality — the attachment analogue of the card-delete gap that just shipped.)_
- **Land the first real external extension (CSV → todos) as a worked example on the contracts** — Strategic gap, not a backlog item: the core keeps gaining engine depth while the work that would DEMONSTRATE the extension thesis is entirely unstarted. There is no landed, external process proving 'anything richer is built on top via the versioned contracts' — the whole bet of the project. CSV → todos with link enrichment (card 078bf24a) is the smallest such proof and is best sequenced immediately after the outbox/webhook seam lands so it can subscribe to real events rather than poll. Doing it will also surface contract ergonomics gaps (idempotency, MCP parity) from the outside-in, which no amount of internal testing reveals. _(user value: Gives users and agents a concrete, copyable pattern for wiring an outside data source into a board — the first answer to 'how do I actually use this with my tools' — and a template the YouTube pipeline (7f56d7c8) and pi-agent (97cec658) examples can follow.)_

Fold parity + a coverage floor into the definition of 'done' before the next feature push rather than accruing it as a reconciliation card. _(user value: The CLI and MCP tools are the primary surfaces for humans, scripts, and agents — under-testing them is where regressions hurt users most and most silently. Parity means an agent using MCP isn't a second-class citizen missing operations a script gets over HTTP.)_

**design-ux**
- [major] The plan's own framing contradicts the 'visible user value per phase' bar: Phases 1-2 are explicitly 'foundation first' and deliver almost nothing a user can see. Phase 1's only genuine user-facing win is the /breaches fix — everything else (ledger reconciliation, registry dispatch, supervisor lifecycle, surface-matrix CI) is internal/developer-facing. Two full phases pass before the marquee value in Phase 3. → Stop claiming every phase ships user value; label Phases 1-2 honestly as enabling/foundation work, AND pull tangible value forward so a user-visible win lands before Phase 3 (see attachments reordering below). Reframe the Phase 1 demo as a regression/developer demo rather than a user-value demo.
- [major] The single most tangible, most user-legible deliverable — attachments end-to-end (attach a file, download byte-identical, see it in the feed, view it on the board) — is parked at Phase 4, even though its only dependency is Phase 1. This buries the clearest 'visible user value' item behind two foundation phases and the entire webhook chain. → Reorder attachments to run as a parallel track starting immediately after Phase 1 (effectively Phase 2). The plan already states it 'can run in parallel from Phase 2 onward' — make the ordering reflect that so the most demoable user win lands early instead of fourth.
- [major] The Phase 2 demo proves a mechanism, not user value: 'start a durable subscriber, kill the server mid-dispatch, restart, watch redelivery' redelivers to an abstract test subscriber because no external consumer exists until Phase 3. It's a compelling engineering demo against a test double, but a user cannot see the payoff until webhooks land. → Either fold the crash-window-closed demo into Phase 3 (where a real webhook receiver makes the redelivery visible), or add a thin end-to-end 'hello webhook' smoke path bridging Phase 2→3 so durability isn't demoed in a vacuum.
- [major] Webhook delivery introduces user-relevant failure state — dead-lettered endpoints, disable-after-N, retry-queue depth, cursor position — but no phase adds any surface to observe it. The plan enforces the failure policy without giving the operator any way to see which endpoints are dead-lettered or how far behind a subscriber is. Enforced-but-invisible failure state is a UX gap. → Add a lightweight delivery/subscriber status surface (e.g. `cards subscribers` / GET /v1/subscribers showing cursor position + dead-letter/disabled state) in Phase 3, and demo it: 'let the endpoint stay down, then show it listed as dead-lettered.' This converts invisible durability into demoable value.
- [minor] Phase 1's demo leads with 'declare a kind=service extension and watch cards serve supervise it' — but a supervised service that does nothing produces no user-observable outcome. As a user-value demo it proves plumbing, not value. → Have the demoed service extension do one observable thing (emit a log line / touch a card / respond on a port) so 'it's now supervised' is visibly true, or drop it from the user-facing demo and keep it as an internal exit-criterion only.

**arch-data**
- [blocker] Phase 2 step 1 says to model the durable subscriber_cursors table 'mirroring the idempotency_keys pattern'. That is the one pattern it must NOT copy: idempotency_keys is dropped on every startup — `DROP TABLE IF EXISTS idempotency_keys` at internal/sqlite/sqlite.go:124, explicitly commented 'ephemeral cache; safe to clear on restart'. A cursor table built on that pattern would be wiped on every restart, which destroys the exact crash-survival property the whole sprint is built to deliver. → Model subscriber_cursors on the DURABLE additive-migration pattern used by condition_marks (CREATE TABLE IF NOT EXISTS, never dropped) and migrateStatusSince/migrateEventsScope (PRAGMA table_info gating). State in the plan: no DROP on init, survives restart, idempotent re-run. Cite condition_marks (sqlite.go:139) as the reference shape, not idempotency_keys.
- [major] The cursor is defined as a single monotonic 'last-delivered event id' with 'advance only on ack', but delivery is at-least-once with retry/backoff and dead-lettering (Phase 3). A single monotonic position forces strict in-order delivery with head-of-line blocking: one failing/dead endpoint freezes the cursor and blocks every later event. The mechanism that unblocks it (dead-letter / disable-after-N) lives in Phase 3, while the cursor semantics are frozen in Phase 2 — so Phase 3 will force a cursor redesign after webhooks already depend on the shape (the plan's own stated 'expensive to walk back' risk). → Design the cursor's advance-past-failure semantics in Phase 2, not Phase 3: decide that dead-lettering an event is what advances the cursor past it, and record that the cursor and the dead-letter policy are one co-designed unit. Pull the retry/dead-letter contract forward into the Phase 2 cursor design or explicitly note the cursor shape is provisional until Phase 3.
- [major] Cursor semantics are ambiguous for FILTERED subscribers. A webhook filtered to (say) status_timeout will scan a long run of unrelated events and deliver none. 'last-delivered event id' then lags far behind 'last-scanned event id' — on every restart the tailer rescans the whole gap. last-delivered and last-scanned are different quantities and the plan conflates them. → Store last-SCANNED id (high-water mark of what the tailer has examined), not last-delivered, so a narrowly-filtered subscriber advances past non-matching events. Make this explicit in the Phase 2 table/CRUD design since it is part of 'the highest-leverage design decision in the batch'.
- [major] The tailer/bus composition seam is under-specified. bus.go is best-effort live fan-out that DROPS slow subscribers (Publish closes the channel on a full buffer). The durable tailer replays from the events log by cursor. 'Composes with (does not duplicate) bus dispatch' does not say which path actually delivers. If the tailer both forwards live bus events and replays the log, you get double-delivery or a gap at the handoff boundary. → Specify the bus as a wakeup-only signal (a 'new event exists' notification) and make the events log the single authoritative delivery source read by cursor. The tailer should never deliver an event body it received off the bus. Also record the dependency on the single-writer invariant (db.SetMaxOpenConns(1), sqlite.go:44) — that is what makes AUTOINCREMENT ids commit in order so an AfterID cursor cannot skip an id committed out of order.
- [major] Domain-concept collision. core already has a type named Subscriber (bus.go:51) — an ephemeral in-process channel listener. Phase 2 introduces a 'first-class named subscriber with a persisted cursor', also in core, with an entirely different lifetime and semantics. Two unrelated concepts sharing the name 'subscriber' inside internal/core will produce lasting confusion in exactly the code (webhooks/tailer) that touches both. → Give the durable concept a distinct name (e.g. Consumer, DurableConsumer, or DeliveryCursor owner) and keep bus.Subscriber for the ephemeral listener. Decide the name in Phase 2 step 1 before the table (subscriber_cursors) and CRUD lock it in.
- [major] Phase 2 step 3 says to make validatePersistConditions 'fail-loud ... error' at load time, but that function today returns non-fatal Warnings by deliberate design (config.go Result.Warnings doc: 'never blocking Load'). The plan's own outcome hedges 'error/warning'. Separately, validatePersistConditions currently only receives ws — it cannot see the extension list — and the new check (durable-subscriber-target ∈ persist_conditions) is a semantically different validation from the existing one (persist_conditions entry is a known type). → Decide fatal-vs-warning explicitly. If fatal (arguably correct, since a durable subscriber on an ephemeral condition silently loses events), state that this deliberately breaks the 'Warnings never block Load' invariant and is a new fatal class. Thread the extensions list into the validator and describe it as an ADDITIONAL check, not an extension of the existing typo check.

**reliability**
- [blocker] The tailer's STEADY-STATE delivery mechanism is unspecified, and 'composes with the existing bus (not a parallel dispatch)' contradicts how the bus actually works. InProcBus.Publish is best-effort and DROPS slow subscribers (closes their channel on a full buffer). So the bus can never be the durable path. The plan only specifies replay 'on connect/startup' — it never says how a live-committed event reaches the tailer without either relying on the lossy bus or being exactly the 'parallel dispatch' it disclaims. The commit-then-crash-window claim is unproven until this is pinned down. → State the model explicitly: the events table is the sole source of truth; the bus is used ONLY as a low-latency wakeup, and every delivery is driven by cursor replay (poll + wakeup), not by consuming bus events. That IS a second dispatch path distinct from the hook supervisor — own that in the design instead of calling it 'composition.' Add a test that drops the bus notification entirely and asserts the tailer still delivers from the cursor.
- [blocker] 'monotonic cursor' + 'at-least-once' + 'dead-letter after N' are listed as independent guarantees but they directly conflict. A single last-delivered-id cursor forces total ordering, so a slow/down endpoint blocks cursor advance and head-of-line-blocks every later event. When you dead-letter event N, advancing the cursor past it breaks at-least-once for N; not advancing stalls the backlog unbounded — the exact failure the dead-letter policy was meant to prevent. → Decide the retry/ordering model concretely: dead-lettered events go to a SEPARATE durable store and the cursor advances past them (at-least-once holds for non-dead-lettered events). Decide whether webhook delivery even needs total ordering — if not, per-event independent delivery avoids head-of-line blocking and a single generic cursor may be the wrong primitive for webhooks specifically (the inverse of the plan's stated over-specialization risk).
- [major] 'Record a retention decision in a doc' is not a safeguard. Durable cursors over an append-only events table mean ANY future trim can strand a cursor that points before the trim horizon — a doc footnote does not prevent that at runtime; it is exactly the kind of silent breaking change the plan says it wants to avoid. → Replace the prose decision with a code-level invariant: a trim must never delete events at id >= min(all subscriber cursors), enforced in the trim path and covered by a test. Ship the guard now even though the trim job itself is out of scope.
- [major] validatePersistConditions today returns Warnings and does NOT fail Load (confirmed in config.go). Phase 2 says 'fail-loud … load-time error/warning' — that error-vs-warning ambiguity is precisely the swallowed-gap risk being mitigated. A warning that scrolls past on serve startup is mitigation theater. → Make a durable subscriber on a non-persisted condition a HARD load error (fail Load), not a warning. If it must stay a warning, specify where/how it is surfaced so it cannot be missed. Note this is a behavior change to the current warn-only contract.
- [major] Upload size ceiling: api.go guards on r.ContentLength, but multipart/chunked uploads can send ContentLength = -1, bypassing a ContentLength check entirely — the new binary-body DoS vector the plan itself flags. Backoff/retry state for webhooks also has no stated durability: if it lives in memory, a restart resets all backoffs and produces a thundering retry storm against endpoints that were being backed off. → Enforce the body ceiling with http.MaxBytesReader (streaming), not a ContentLength comparison; enforce the MCP base64 ceiling before decode/buffering. Specify per-subscriber worker isolation with bounded in-flight, and persist retry/attempt state so backoff survives restart.
- [major] The crash-window exit criterion ('forced-failure test proves the crash-window is closed') as demoed by 'kill the server mid-dispatch' is inherently flaky and hard to make deterministic in CI — process-kill timing between commit and fan-out is a race. → Design a deterministic fault-injection seam (a hook between commit and bus fan-out that the test can trigger) so the crash-window test asserts redelivery-from-cursor without racing a real SIGKILL. Specify this seam in Phase 2, not as an afterthought.
- [major] Phase 1 is overloaded and sits on the critical path for ALL later phases, and it bundles a net-new surface-matrix generator + CI parity gate that is unrelated to the durable-coordination spine. Building a new blocking CI gate here and then racing to make it 'fully green' in Phase 5 lets doc/parity churn block the sprint's actual value. → Trim Phase 1 to the true foundation (kind-registry dispatch + DEBT-29 shutdown-ctx binding). Float the ledger reconciliation, /breaches fix, and surface-matrix work as independent tracks. Ship the parity check report-only (non-blocking) first; promote it to a gate after the sprint, not mid-sprint.

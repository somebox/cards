## Pitch

The last several sprints drifted onto the web board — 'only one view over the same API.' This sprint rotates the center of mass back onto the differentiating substrate: the four transports as honest, versioned contracts, and the extensions-over-plugins bet. It is deliberately a platform arc with four different demo audiences — agent (P2), definition author (P3), board viewer (P4), extension developer (P5) — stated up front so the value ordering reads as a choice: drain the review queue and retire doc drift first (with an executable guard so the drift can't recur), harden the config-validation and reload seams every later phase leans on (fixing a live stale-generation bug in the process), then land the two user-visible wins in PARALLEL (live authoring with in-browser failure feedback; enum-driven board legibility), and finish with the north-star supervised service kind whose hard sub-problems — lifecycle vocabulary, drain semantics, reconcile-on-reload — are named steps, not sub-bullets. Every schema change is additive omitempty JSON in the definition layer: no migrations, no snapshot-format change.

## Phase 3 — Live authoring loop: definitions/ file-watching on the reload seam

**Goal:** Audience: the definition author with a BROWSER open. Runs in parallel with Phase 4 (both depend only on Phase 2); drawn alongside it because the reload contract is Phase 5's prerequisite.

**Depends on:** Phase 2

**Steps:**

1. Fix the supervisor↔generation coupling FIRST — it is a live bug today, and the watcher makes reload frequent: the hook supervisor at cmd/cards/serve.go:130 captures the initial *core.Service, and reloadLocked() (cmd/cards/reload.go) closes that generation, leaving the captured svc pointing at a Closed service for every GetCard in cardBoardMembership/cardTypeID (internal/hooks/hooks.go).    - **Outcome:** After any reload, hook condition-evaluation runs against the live generation, not a closed one; the supervisor↔generation provenance rule is written down where Phase 5 will read it.
   - **Touches:** cmd/cards/serve.go, cmd/cards/reload.go, internal/hooks/hooks.go, reload-contract note
2. Add an optional --watch flag wiring a definitions/ watcher into reloadableApp.reloadLocked(). Dependency-free poller modeled on scripts/dev-server.sh's fingerprint-hash loop (no fsnotify, per principle 10) — designed for testability from the start: injectable clock and a synchronously-drivable scan function so debounce/coalescing/self-write tests assert deterministically without real sleeps or -race flake. Self-write suppression uses a suppression token set by handleCreateBoard's write-then-reload path, NOT sharing reloadableApp.mu with the poll loop, so the poller can never block the HTTP write path.
   - **Outcome:** Saving a card-type or board JSON reloads the Service around the SAME bus; live SSE clients survive; a burst of editor saves (atomic unlink+create, save-all) coalesces to exactly one reload; handleCreateBoard's own write doesn't double-fire.

   - **Touches:** cmd/cards/reload.go, internal/httpapi/ui.go + templates, docs/architecture/ARCHITECTURE.md (or a new ADR)

## Phase 5 — Composition made real: supervise the 'service' extension kind

**Goal:** Audience: the extension/integration developer — judged on 'an external process I wrote in any language survives crashes and consumes events', not an end-user bar. Turn 'extensions over plugins' into working mechanism. The lifecycle-schema ADR is this phase's first step, authored before the supervisor code (and startable early, during Phase 3's window, since it depends only on Phase 2) so the load-bearing vocabulary isn't rushed into the first supervisor PR.

**Depends on:** Phase 3

**Steps:**

1. Write the lifecycle-schema ADR covering the FULL vocabulary as one model, since config.Extension is shared by all three kinds: (a) RestartPolicy (on-failure/always/never + bounded backoff shape) reconciled with the existing Autostart bool — Autostart is the enable-gate, RestartPolicy the recovery shape; (b) RestartPolicy on kind:hook or kind:run is a load-time REJECTION per Phase 2's fail-loud rule, not a silent no-op; (c) the service-vs-run boundary stated (long-running-supervised vs one-shot); (d) the event-delivery boundary: services dial /v1/events/stream as API clients (per EXTENSIONS.md), making the one supervisor deliberately bimodal — hooks get in-process bus + subprocess-per-event, services get pure process lifecycle and NO event feeding — recorded as intentional so no later 'cleanup' unifies them. `expose` stays untouched.
   - **Outcome:** config.Extension gains a validated RestartPolicy with load-time rejection of unknown values AND of the field on non-service kinds; the bimodal supervisor and SSE-client boundary are recorded decisions.
   - **Touches:** internal/config/extensions.go, docs/extensions/EXTENSIONS.md, docs/architecture/ARCHITECTURE.md (ADR)
2. Build the supervised-process class with real lifecycle semantics: (1) listener-ready gate — start services only after the net.Listener is accepting (create the listener before the supervisor goroutine, or pass a readiness channel); hand each child the loopback base URL via env so 'how does the service find the server' is defined, not assumed; (2) bounded backoff WITH a minimum-healthy-uptime threshold before the counter resets, so a runs-briefly-then-crashes service escalates to the cap instead of pinning CPU — crash-loop test required; (3) bounded drain: SIGTERM, wait a configurable grace period, then SIGKILL the process group (reusing hooks.go's procgroup fallback) — a SIGTERM-ignoring child must be force-killed within the grace window, test required; (4) ONE shared supervisor-construction path used by both `serve --run-extensions` (serve.go:130) and standalone `run-extensions` (extensions.go:56), with the ADR naming `serve --run-extensions` as the supported home. Budget explicitly for mac+linux race-clean signal tests (fake crashing/hanging child binaries) — the procgroup_unix/other split shows this doesn't come free.
   - **Outcome:** kind:service autostarts after the listener accepts, restarts per policy without crash-loop CPU pinning, force-kills a hung child within the grace window, and both entry points share one wiring.
   - **Touches:** internal/hooks/ (sibling supervisor file), cmd/cards/serve.go, cmd/cards/extensions.go, supervisor tests
3. Reconcile-on-reload as its own design + implementation: config.Result.Extensions is rebuilt per generation while the supervisor lives outside the reloadable seam. Define the service identity key (extension ID; a change to command/args/env hashes as 'same service, changed declaration'), the decision table (added → start; removed → drain+stop; unchanged → leave alone; declaration-changed → drain+restart), and the concurrency model: reload swap holds reloadableApp.mu, the supervisor reconciles from a snapshot handed off AFTER the swap completes — never acquiring mu from the supervise loop, so no HTTP-handler deadlock. Tests: board-creation reload leaves running services untouched; edited declaration restarts exactly that service; removed declaration stops it.
   - **Outcome:** Routine board-creation reload does NOT churn children; genuine declaration changes are handled per a documented table. Flip INTEGRATOR-REFERENCE.md §7 to [built] with the audit changelog updated.
   - **Touches:** cmd/cards/reload.go, internal/hooks/ supervisor, reconcile tests, docs/reference/INTEGRATOR-REFERENCE.md

**Demo:** Declare a tiny SSE-subscriber service (a few lines in any language) in extensions.json; run `cards serve --run-extensions`; mutate a card in the UI and watch the external process print the event. Kill the process — supervisor restarts it per policy. Replace it with a script that crashes instantly — backoff escalates to the cap instead of spinning. Create a board in the UI — the service is NOT restarted.

**Exit criteria:**

- kind:service autostarts behind a real listener-ready gate; RestartPolicy validated at load, rejected on non-service kinds
- Crash-loop reaches backoff cap (min-healthy-uptime reset rule tested); SIGTERM-ignoring child SIGKILLed within grace window; shutdown always returns
- Reconcile-on-reload: identity key + decision table implemented and tested; board-creation reload churns zero services
- SSE-client event boundary + bimodal supervisor recorded in ADR; both run-extensions entry points share one wiring; INTEGRATOR-REFERENCE.md §7 flipped to [built]; go test ./... green and race-clean on mac+linux

## Risks & de-risking

- Every schema change this sprint (FieldDef.OptionThemes, BoardPresentation.StyleField, Extension.RestartPolicy) is an additive, omitempty, definition-layer JSON field — zero SQLite migrations, zero backlog.jsonl format change. This is the sprint's main de-risking property; any step that threatens it (e.g. strict key parsing) is out of contract.
- Phase 2's stricter validation is a load-contract change: the blocker case is 'my board won't boot after a binary upgrade.' Mitigated by validating demo-workspace and known definitions before the rejection ships and by the warn-now/reject-next-sprint tier for ambiguous cases — but third-party workspaces we can't see remain the residual risk; the warning tier is the pressure valve.
- The supervisor's stale-generation reference (serve.go:130 capturing a svc that reloadLocked() later closes) is a live bug that Phase 3's watcher would amplify from rare to constant. It is fixed as Phase 3's first step; if Phase 3 slips, that one step should be cherry-picked forward anyway.
- The reload contract (debounce, self-write suppression via token not lock-sharing, supervisor provenance, definition_reload_failed) is a shared seam for the watcher AND the Phase 5 supervisor. Phase 3 writes it down as a note with no open questions left — the earlier draft's deferred failure-channel decision is now decided in-phase.
- The lifecycle-schema ADR (RestartPolicy × Autostart × three kinds) is a documented contract the moment it ships (principle 8). It is Phase 5's first step and may be started early during Phase 3's window (it depends only on Phase 2), authored before the supervisor code — if the sprint compresses, cut Phase 5 implementation scope before cutting the ADR.
- Phase 4's render-path unification touches every existing board; the golden-render harness (new, budgeted infra) is the first step and the byte-identical gate, not a footnote. If the harness proves expensive, the fallback is snapshotting only the type-themed demo boards — enough to catch a re-skin.
- Watcher and supervisor tests are the two most flake-prone surfaces in the sprint (timing + process signals, respectively). Mitigations are designed in, not hoped for: injectable clock / synchronous scan driving for the watcher; fake child binaries + explicit mac/linux budget for signal tests (the procgroup_unix/other split proves this costs real time).
- The pipeline is review-bound: Phase 0-1 is a hard gate before M-sized work, and its per-card verification (not batch-flipping) is what keeps the gate honest.
- The parity test is an allowlist, not automation — it guarantees a reviewed partition of Service methods and a doc that can't silently drift, nothing more. Treat allowlist edits in review as contract changes.
- Phase 5 remains the phase with the most unknowns at the end of the critical path (0-1 → 2 → 3 → 5). The ADR-early scheduling and the promoted reconcile-on-reload step are the mitigations; if Phases 2-3 slip badly, ship Phase 5 as supervisor-without-reconcile (services restart on every reload, documented) rather than slipping the whole north star.

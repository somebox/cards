## Theme

v0.1.0 shipped, but post-release energy is drifting toward UI polish while the
load-bearing surface — the agent coordination loop and its contracts — still has
silent asymmetries. This sprint lays two foundations (uniform card-reference
resolution across every write verb and all three transports; a loop that works
out of the box with reachable attachments), fixes the two real defects hiding in
the attach path (missing version contract, orphaned-blob leak), and cashes them
out as ONE complete board capability: accessible browser attachment upload with
full interaction states. Honest audience framing: Phases 1-3 serve the agent/CLI
user, Phase 4 serves the board user. The remaining groomed UI cards move to a
follow-on sprint — they are follower-SEQUENCED, not low-effort, and bundling
them was the reviews' shared scope objection.

## Test infrastructure (cross-cutting, applies to every phase)

Every test added this sprint must be self-contained and repeatable, following
the conventions already in the suite: stores are in-memory
(`sqlite.Open(":memory:")` via the `newTestService*` harnesses) or backed by
`t.TempDir()`; fixtures are created by shared, exported helpers with teardown
via `t.Cleanup` (never manual state, env vars, or run-order dependency); large
payloads are generated programmatically in-test (`bytes.Repeat`), never
committed as fixture files; and integrity checks (doc-id, definition sync) land
as ordinary Go tests in the `internal/docaudit` pattern so `go test ./...`
remains the one command that runs everything — locally and in CI, with no extra
workflow or setup step.

### Phase 1 — Uniform card-reference resolution (short-id parity across all three transports)

Make 'a card reference is a full id OR a last-8 short id' the universal Service
contract for every write verb, with ambiguity rendered as ONE structured error
across HTTP, directcli, and MCP. Audience: the agent/CLI user — this phase is
invisible on the board and is framed that way deliberately. The taxonomy fold is
now mandatory (not 'preferred'): MCP does not share the HTTP router
(mcp.go:293/:442 call the Service directly and render via toolError ->
core.AsError at mcp.go:203), so an httpapi-only helper would leave MCP emitting
generic -32603 on ambiguous ids.

- Fold AmbiguousIDError into the core.Error taxonomy FIRST, before touching any
verb, and reconcile all THREE existing divergent representations in one commit.
Keep the existing code string 'ambiguous' (not 'ambiguous_id') to preserve the
GET/UI wire contract, and add a Candidates []string field to core.Error with
omitempty so every other error's serialized shape is unchanged. Update every
consumer in the same commit: delete apiGetCard's bespoke
{error:'ambiguous',query,candidates} branch (internal/httpapi/api.go:117-126) so
one canonical rendering path remains, replace ui.go:496's hand-built
core.Error{Code:'ambiguous'}, verify card_ambiguous.html still receives
candidates, and grep tests for the old 'query' field. Record the one intentional
body change (GET's 'query' field becomes the standard core.Error shape) in the
commit message as a contract note.
  **Outcome:** Exactly one ambiguous-id wire shape exists (code 'ambiguous' +
  candidates), rendered identically by HTTP, directcli (shared router), and MCP
  (via core.AsError now recognizing the taxonomy error). Ambiguous short id on
  DELETE — a live bug — returns 409-style structured error, never a 500.
  Files: `internal/core/errors.go`, `internal/core/types.go (AmbiguousIDError)`,
  `internal/httpapi/api.go:117-126`, `internal/httpapi/ui.go:496`,
  `internal/httpapi/templates/card_ambiguous.html`, `internal/mcp/mcp.go:203`

- Add a Service-layer resolve-for-write helper (ResolveCard-backed) that
preserves getCard's deliberate error discipline — ErrNotFound maps to not_found,
every OTHER store error stays a 500-class error (the :609 comment documents this
as a fixed past bug; the helper must not collapse store failures into not-
found). Swap ALL twelve mutation call sites in one pass: PatchCard (:695),
UpgradeSchema (:895), AppendEntry (:980), UpdateEntry (:1023), RemoveEntry
(:1067), AddLink subject (:1098), RemoveLink (:1156), AddComment (:1191),
AddArtifact (:1228), EditComment (:1280), Claim (:1320), Release (:1351), plus
History's existence check (:1473). DeleteCard already uses ResolveCard (:849)
and only needs step 1's error mapping. Also resolve AddLink's SECOND id,
in.Target (:1114), through the same helper — path ids and payload ids behave
identically.
  **Outcome:** cards patch/comment/append/claim/release/upgrade/link/attach all
  accept short ids, including link targets; directcli and MCP inherit resolution
  at the Service layer. No write verb masks a store failure as not-found.
  Files: `internal/core/service.go (getCard :612 and the 14 getCard call sites
  listed: 12 mutations + History + AddLink.Target)`, `docs/reference/DEVELOPER-
  REFERENCE-CLI.md`

- Extract the deterministic-ambiguity fixture BEFORE writing the parity tests.
The seam already exists and is proven: TestResolveCard_AmbiguousError
(service_test.go:~990) seeds two cards with crafted colliding last-8 ids via
direct st.InsertCard against the in-memory store — no injectable ID generator
on the Service/store is needed (that would be a production seam serving only
tests; do NOT add one). Lift the pattern into a shared, exported helper —
e.g. coretest.SeedCollidingCards(t, store, suffix) returning both ids, with
t.Cleanup teardown — so the service, httpapi, MCP, and CLI parity tests all
consume ONE fixture instead of re-crafting ids per package. Then write one
table-driven test over every converted verb with four rows: short-id hit,
ambiguous (deterministic via the helper), not-found, and non-NotFound store
error (pinning the 500-vs-404 property). Add one MCP-path and one CLI-path
ambiguous test asserting the Candidates slice actually surfaces in those
renderers, not just code+message.
  **Outcome:** The ambiguous branch is deterministically reproducible from any
  package through one shared fixture helper (setup + teardown automated, plain
  `go test ./...`); each write verb has short-id/ambiguous/not-found/store-error
  coverage; the 'clear error listing both full ids' claim is verified on all
  three transports.
  Files: `internal/core/coretest (new, or exported helper beside the existing
  harnesses)`, `internal/core/service_test.go`, `internal/httpapi/api_test.go`,
  `internal/mcp (test)`, `internal/cli (test)`

**Demo:** In a fresh workspace: cards get 3f2a9c1b, cards patch 3f2a9c1b
--status=in_progress --version 1, and cards comment 3f2a9c1b 'working' all
succeed with the same short id; a fixture with two colliding short ids returns
the same structured 'ambiguous' error with both candidate ids from the CLI, the
HTTP API, and an MCP tool call — not a 500 or a bare -32603.

**Exit criteria:**
- AmbiguousIDError is folded into the core.Error taxonomy; apiGetCard's bespoke
branch and ui.go:496's hand-built error are deleted — grep confirms a single
rendering path.
- Code string stays 'ambiguous'; Candidates is omitempty so no other error's
serialized shape changes; the GET body change ('query' field dropped) is
recorded as an intentional contract note.
- All 12 mutation sites plus History and AddLink.Target route through the
resolve helper; grep for s.getCard in write methods returns only the helper.
- The shared colliding-id fixture helper exists with automated setup/teardown
and is consumed by all four packages' tests (no per-package id crafting, no
production ID-generator seam); table-driven tests cover short-
id/ambiguous/not-found/store-error per verb; MCP and CLI tests assert candidates
are surfaced; full suite green.

### Phase 2 — Loop works out of the box (workspace targeting + reachable attachments)

Turn two built-but-hidden capabilities on for the agent/CLI user: one shared
workspace-resolution rule that accepts either the project root or its .cards
child, and an artifact field in the shipped starter type so 'cards attach' is
reachable from a fresh install. Honestly scoped: this fixes FRESH inits; pre-
existing workspaces (including the repo's own dogfood board) keep their old card
types until manually upgraded.

*Depends on: Phase 1*

- Extract ONE shared workspace resolver used by all three discovery paths — the
--workspace flag / $CARDS_WORKSPACE (resolveWorkspaceDir), init's positional
arg, and git-repo discovery — so the 'where is the workspace' rule cannot
silently diverge across them. Accept both a workspace root and its .cards child.
When BOTH X and X/.cards look like valid workspaces, FAIL with an actionable
hint rather than silently picking one — guessing wrong is worse than erroring.
Note the honest framing: pointing --workspace at a project root already fails
loudly today; this is accept-either-path convenience plus a better hint, not a
fix for silent empty opens.
  **Outcome:** cards --workspace ./myproject and ./myproject/.cards open the
  same workspace via the same resolver init and git-discovery use; the both-
  valid case errors with a 'did you mean X/.cards?' hint. Usage text and CLI
  reference change atomically with the code.
  Files: `cmd/cards/workspace.go (resolveWorkspaceDir`, `findDotCards)`,
  `cmd/cards/serve.go and cmd/cards/directcli.go (callers)`, `cmd/cards/init.go
  + cmd/cards/main.go (init path + usage string)`, `docs/reference/DEVELOPER-
  REFERENCE-CLI.md`

- Add an artifact-typed field to the shipped starter card type (schema_version
stays 1; Scaffold never clobbers existing workspaces). Add a one-paragraph
upgrade note to the CLI reference for pre-existing workspaces: edit the card-
type JSON or run UpgradeSchema — so the fresh-vs-existing asymmetry is
documented, not surprising.
  **Outcome:** cards init NEW && cards attach <card> <file> works end-to-end
  from a fresh install; existing workspaces have a documented one-step upgrade
  path.
  Files: `internal/starter/assets/definitions/card-types/task.json`,
  `docs/reference/DEVELOPER-REFERENCE-CLI.md`

- Resolve the starter-vs-examples duplication in the SAME change: examples/demo-
workspace maintains independent card-type JSON with no artifact field. Update
the demo definitions in lockstep AND add a sync check as an ordinary Go test in
the internal/docaudit pattern (doc-integrity checks that run inside `go test
./...` — no new CI workflow, no manual step), failing with a diff when the demo
card-type JSON diverges from internal/starter/assets on the fields both must
share.
  **Outcome:** examples/demo-workspace card-type JSON declares the same artifact
  field as internal/starter/assets; the sync test fails the ordinary test run if
  the two diverge — repeatable locally and in CI with zero setup.
  Files: `examples/demo-workspace/definitions/card-types/*.json`,
  `internal/docaudit (sync test)`

- Add dedicated unit tests for the shared resolver — root acceptance, .cards
acceptance, the both-valid failure with hint, and the empty/missing hint — plus
confirmation that init and git-discovery route through it. Each case builds its
directory layout in t.TempDir() via a small fixture helper (mkWorkspace(t, dir,
layout)), so setup and teardown are automatic and the cases are trivially
extendable.
  **Outcome:** Direct coverage for every resolution branch including the
  deliberate both-valid error, from self-contained temp-dir fixtures; full
  suite green.
  Files: `cmd/cards/workspace_test.go (new)`

**Demo:** From an empty dir: cards init proj, then cards --workspace ./proj
attach <short-id> ./diagram.png attaches a file (using the Phase-1 short id and
root-path acceptance) and it is retrievable; a directory containing both a
workspace and a .cards child produces the actionable-hint error rather than a
silent guess.

**Exit criteria:**
- Starter type declares an artifact field; cards attach works from a FRESH cards
init with no manual schema edit; the existing-workspace upgrade note is in the
CLI reference.
- One shared resolver serves --workspace, init, and git discovery; both-valid
targets error with an actionable hint; usage text + docs updated in the same
commit.
- examples/demo-workspace no longer diverges from starter assets (synced or CI-
checked).
- cmd/cards/workspace_test.go covers all resolution branches including the both-
valid failure; full suite green.

### Phase 3 — Contract-honesty checkpoint (decisions recorded, behavior fixed)

A decision checkpoint, labeled as such (not dressed as a user demo): make the
normative contracts true before the ~25 modified docs files in the working tree
re-encode false claims, and fix the two real defects the reviews surfaced in the
attach path — the missing version parameter and the orphaned-blob leak — BEFORE
the browser UI makes them common. Corrected framing per review: AddArtifact does
NOT last-write-win today; the store's CAS (sqlite.go:571 UPDATE ... WHERE
version=?) already rejects the second writer with a version_conflict it had no
version param to anticipate, and artifacts.Put writes blob bytes BEFORE the CAS
commit, leaking an orphan on every lost race. The true failure mode is field-
metadata clobber/conflict, not byte loss (blobs are content-addressed).

*Depends on: Phase 1*

- DECIDE: docs say JSON-only for definitions. Both technical reviews demolished
the 'cheap yaml fallback' premise — go.mod has no yaml dep (extensions.go:168 is
a hand-rolled parser), the structs are json-tagged so naive gopkg.in/yaml.v3
would silently drop fields, config.go:120/:159 never even enumerate .yaml files,
and config.go:2 documents JSON-only-except-extensions as deliberate intent. The
code is self-consistent; only SPEC/ARCHITECTURE/DEVELOPER-REFERENCE/README
drifted. Correct the docs (keeping the extensions.{yaml,json} exception
accurate) and pin the contract with a test asserting a .yaml card-type
definition in the definitions dir is not loaded.
  **Outcome:** Docs and code agree on JSON-only definitions, pinned by a test;
  no new parse surface, no new dependency.
  Files: `docs/spec/*`, `docs/architecture/*`, `docs/reference/*`, `README.md`,
  `internal/config/config_test.go`

- Give AddArtifact a first-class optimistic-concurrency contract, AND specify
the transport now (the coupling Phase 4 depends on). Version is an OPTIONAL
guard mirroring DeleteCard (:264, not the required-version verbs): omitted → the
write proceeds against the current card, so Phase 2's fresh-install `cards
attach <id> <file>` demo stays valid; supplied → a mismatch is rejected. The
request body is the raw file bytes, so version travels as ?version=N on POST
/v1/cards/{id}/artifacts/{field}. Service-side, mirror the existing two-layer
pattern — WHEN a version is supplied, pre-check version != current.Version for a
clean 409 carrying CurrentCard, with the store's WHERE-version CAS as backstop.
In the same change fix the orphaned-blob leak: move s.artifacts.Put after the
CAS commit succeeds, or clean up the blob on commit failure. Add a two-
concurrent-attach Service test (both writers supplying version) asserting the
loser gets version_conflict and no orphan blob remains — the no-orphan check
enumerates the t.TempDir()-scoped artifacts dir after the race, so the
assertion (and its teardown) is fully self-contained.
  **Outcome:** The optimistic-concurrency contract holds for AddArtifact with a
  pinned transport (?version=N, optional); when a version is supplied, losing
  writers get a clean 409 with CurrentCard; version-less attach still succeeds;
  failed commits leave no orphaned blobs.
  Files: `internal/core/service.go (AddArtifact :1224)`,
  `internal/httpapi/api.go (apiAddArtifact)`, `internal/cli/commands.go
  (cmdAttach :473 passes optional ?version=N)`, `internal/core/service_test.go`,
  `docs/spec/SPEC-API-SURFACE.md`

- Fix the stale doc comment in internal/artifacts/artifacts.go ('No HTTP
endpoint calls into this package yet' — false since the attach route landed).
Separately verify DEBT-54/55 (Go 1.26 toolchain, golangci module path) are
already resolved in-tree — verification only, explicitly NOT a gate on this
phase's exit.
  **Outcome:** Package doc reflects reality; DEBT-54/55 confirmed closed without
  diluting the phase.
  Files: `internal/artifacts/artifacts.go (package doc)`

**Demo:** Decision checkpoint, demonstrated by running the pinning tests live:
the config test showing a .yaml card-type is ignored per the now-honest docs,
and the concurrent-attach test (both writers supplying ?version=N) showing the
second writer receives a clean version_conflict with CurrentCard and no orphaned
blob — both previously unpinned behaviors.

**Exit criteria:**
- Docs claim JSON-only for definitions (extensions exception intact) and a test
pins that a .yaml definition is not loaded; no yaml dependency added.
- AddArtifact accepts an OPTIONAL ?version=N (omitted → proceeds against
current; supplied → pre-checks for a clean 409 with CurrentCard); the blob write
is ordered after (or cleaned up on) CAS failure; the two-concurrent-attach test
passes.
- The recorded decision states the true failure mode (field-metadata conflict;
blobs are content-addressed) — not the fictional 'last-write-wins'.
- artifacts.go doc corrected; DEBT-54/55 verified resolved (non-gating).

### Phase 4 — The second view: browser attachment upload, whole feature

Cash out Phases 1-3 as the board user's first capability that previously
required the CLI — designed as a complete interaction, not a happy path. Full
state machine, accessible primary control, explicit error surfaces, and honest
live-ness: the board grid is SSE-live, the modal is refresh-on-mutation with a
stated staleness limitation. This is the first board-visible phase, and the
sprint says so plainly — Phases 1-3 serve the agent/CLI user.

*Depends on: Phase 2, Phase 3*

- Build the upload control with click-to-browse as the PRIMARY control (visible
<input type=file>, keyboard- and touch-reachable, matching the modal's existing
a11y bar) and drag-drop as an enhancement scoped strictly to the open modal —
never the board card, so it cannot collide with the existing column-move drag
gesture (layout.html:162-185). The empty artifact field's bare '—'
(card_modal.html:~87) BECOMES the upload affordance (drop zone + browse button),
fixing the discoverability gap. Single file per field; multi-file drops rejected
with a message. POST the File as a RAW body (not multipart — the natural
FormData instinct will 400) to POST /v1/cards/{id}/artifacts/{field}?version=N
per Phase 3's transport decision, always supplying the loaded card's version.
  **Outcome:** A keyboard-only user can upload without dragging; the empty field
  advertises the capability; the wire format matches the CLI exactly and always
  includes the version param.
  Files: `internal/httpapi/templates/card_modal.html`,
  `internal/httpapi/templates/layout.html (client JS)`,
  `internal/httpapi/render.go (artifactView)`

- Implement the full upload state machine: (1) idle affordance, (2) drag-over
highlight on the modal drop target, (3) uploading indicator, (4) success
(artifact renders), (5) explicit errors reusing the modal's existing .alert
element — client-side >32MiB pre-check before POST, server 400/413, and
version_conflict rendered as 'this card changed — reload' (the honest answer to
the two-tabs scenario instead of SSE-subscribing the modal).
  **Outcome:** Every failure a user can cause has a visible, worded outcome; a
  drop never silently does nothing.
  Files: `internal/httpapi/templates/card_modal.html`,
  `internal/httpapi/templates/layout.html (client JS)`,
  `internal/httpapi/templates/style.css`

- Extract ONE shared 'refresh the modal after a non-PATCH mutation' JS helper
(the board grid is SSE-subscribed; the open modal is not). The helper defines
the two edge behaviors the reviews flagged: if the post-upload refetch fails,
show an error and keep the modal (never a stale modal masquerading as current),
and guard against the SSE board-refresh racing the manual modal refetch into a
double render. Built shared because the deferred comments/entries card needs the
identical pattern.
  **Outcome:** After upload the modal reflects the new artifact without a page
  reload; refetch failure and SSE races have defined behavior; the helper is
  reusable by the follow-on UI sprint.
  Files: `internal/httpapi/templates/layout.html (shared helper)`,
  `internal/httpapi/ui.go`

- Render artifacts on the board card partial mirroring the modal's existing
image-vs-download branch (card_modal.html:85): image thumbnails with a fixed
max-height consistent with the existing .artifact-thumb 240px cap
(style.css:306) so card rhythm is preserved, and a file/download chip for non-
image artifacts so they are not invisible at grid level. Appears live via the
existing SSE artifact_added subscription.
  **Outcome:** Uploaded artifacts of ANY type are visible on the board card live
  after upload, without disturbing grid density (thumbnails capped at the
  existing 240px, non-image types shown as a download chip).
  Files: `internal/httpapi/templates/card_partial.html`,
  `internal/httpapi/templates/style.css`, `internal/httpapi/ui.go`

- Tests: httpapi upload round-trip (raw body + version param); oversize >32MiB
request returns a typed too-large error, not a 500 (http.MaxBytesReader at
api.go:381 errors mid-stream and today likely falls through AsError as 500 — pin
a clean response for both CLI and browser); stale-version upload returns the
Phase 3 409 shape the UI renders. The oversize payload is generated in-test
(bytes.Repeat / io.LimitReader over a zero reader) — never a committed fixture
file — and all cases run against the existing t.TempDir()-backed httpapi
harness, so the whole matrix is `go test ./...`-repeatable.
  **Outcome:** Happy path, oversize, and conflict paths are all pinned end-to-
  end with self-contained, generated fixtures; behavior matches the Phase 3
  contract.
  Files: `internal/httpapi/api_test.go`

**Demo:** Browser-only, on a fresh workspace: open a card, click Browse (no
dragging) and upload a PNG — progress shows, the modal updates, and a thumbnail
appears live on the board card; then drag a 40MiB file onto the modal and get an
immediate, worded 'too large' error with no network round-trip; finally, upload
from a second tab and watch the first tab's stale upload get a 'card changed —
reload' message instead of a silent clobber.

**Exit criteria:**
- Click-to-browse upload works keyboard-only; drag-drop is modal-scoped and
cannot collide with the board's column-move gesture.
- All five interaction states (idle/drag-over/uploading/success/error) are
implemented; the empty artifact field advertises how to upload; errors reuse the
modal's .alert.
- Oversize returns a typed error client-side (pre-check) AND server-side (no 500
from MaxBytesReader); stale version renders the reload affordance; modal non-
live-ness is documented behavior.
- Board card shows thumbnails for images (capped at 240px) and download chips
for other types, live via SSE; upload round-trip + oversize + conflict tests
pass; full suite green.

## Risks

- core.Error gains a Candidates field: even with omitempty and the preserved
'ambiguous' code string, any consumer doing strict shape validation could
notice; the one intentional break (GET's bespoke 'query' field) must be hunted
in tests and called out in the commit, not discovered downstream.
- The resolve-for-write helper could regress the deliberately-fixed store-error
masking bug (getCard :609): non-NotFound store errors must stay 500-class. The
store-error row in the table-driven test is the guard — do not skip it to save
time.
- Without the ID-generator/fixture seam, the ambiguous branch of the parity
tests is nondeterministic and will quietly become 'asserted, not verified' — the
exact failure Phase 1 exists to fix. The seam lands before the tests, not after.
- Phase 3's blob-ordering fix (Put after CAS commit) changes AddArtifact's
failure atomicity; verify the artifact store tolerates commit-then-put ordering
or implement cleanup-on-failure instead — pick one in code review, don't ship
both half-done.
- Phase 4 wire-format trap: FormData/multipart is the natural browser instinct
and will 400 against the raw-body handler; the ?version=N transport decided in
Phase 3 must land before the widget is written or the two get redesigned mid-
flight.
- Attach's version is an OPTIONAL guard (mirroring DeleteCard), not required:
the browser must always send it, but the CLI's version-less `attach <id> <file>`
must keep working — a dev who mistakenly makes it required will break Phase 2's
fresh-install demo.
- File-drop and card-drag share the HTML5 drag-and-drop API; the modal-only
scoping must be enforced in code (drop handlers on the modal container only,
dragover suppressed elsewhere) or files dropped on the board will trigger the
column-move path or browser navigation.
- UI gravity remains even with Phase 5 cut: the uncommitted working-tree UI
changes (render.go, card_partial.html, style.css) will tempt an early commit;
they land with the follow-on UI sprint, on top of Phase 4's foundation, not
ahead of it.
- Sequencing: Phases 1-3 deliver no board-visible change. That is now stated
honestly (agent/CLI audience) rather than hidden — but it means truncating the
sprint after Phase 3 ships contract value only. Phase 4 is the payoff and is
sized to fit because Phase 5 was cut.

## Out of scope

- Phase 5 UI cards (in-modal comments/entries editing, new-card modal, new-board
flow, board-settings editor, polish pass, landing the uncommitted working-tree
UI changes) — cut to a follow-on sprint per the reliability review: this was 2-3
sprints labeled one, and each of these is a distinct design problem needing its
own form/validation/empty/error states, not a 'cheap follower'. The design
review's ask to split them into separately-demoed deliverables is satisfied by
deferring them wholesale; the shared modal-refresh helper and short-id API from
this sprint remain their foundation.
- YAML parsing for definitions — DECIDED OUT (was conditional). Both technical
reviews established the 'cheap fallback' premise was false: go.mod has no yaml
dependency, structs are json-tagged (naive yaml.Unmarshal silently drops fields;
only sigs.k8s.io/yaml would work), config.go:120/:159 enumerate .json only, and
config.go:2 documents JSON-only-except-extensions as deliberate intent. Phase 3
corrects the docs to match the code.
- Subscribing the open card modal to SSE — declined (design minor). The refresh-
after-mutation helper plus surfacing version_conflict as a 'card changed —
reload' message covers the two-tabs case far cheaper; the modal's non-live
nature is stated honestly in Phase 4 instead. Revisit only if stale-modal
reports appear in dogfooding.
- MCP integration test for the upload path specifically — declined (arch
suggestion). MCP calls the Service directly, and Phase 3's Service-level
concurrent-attach test plus Phase 1's MCP ambiguous-id test already pin the
transport-parity claims; a bespoke MCP upload test adds ceremony without new
coverage.
- Durable outbox/tailer + webhooks (Sprint B) — held at the pre-registered NO-
GO; SUBSCRIBERS.md stays cold until a real consumer is observed losing events.
- Auth / AUTH.md RFC and any permissions/authz work — 'needs-design' and a
stated indefinite non-goal; host's responsibility per the philosophy.
- GH-Pages MkDocs microsite + deploy Action + landing page — not on the critical
path and adds contract-honesty surface.
- Wiring the orphaned View type (saved/filtered views) — decide-or-drop in a
later sprint.
- Hook-payload contract ambiguities DEBT-45/46 — defer, but record a decision
deadline before the next extensions-facing release.
- Bulk/batch write verbs (bulk-move, bulk-tag) — the Phase 1 resolve helper is
their foundation, but they are not in this sprint.
- Coverage backfill for cmd/cards (28.8%), internal/seed,
internal/core/eventlogtest, and the /v1/breaches temporal-coverage gap —
timeboxed out.
